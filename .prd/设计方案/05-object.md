## 1. 仓储接口

```go
// repository/object.go
type Object interface {
	// GetObjectByMd5 去重判定（命中即秒传），必须带 store_keyword 限定
	GetObjectByMd5(ctx core.Context, storeKeyword, md5 string) (*entity.Object, error)
	// GetObject 按主键查询
	GetObject(ctx core.Context, id uint64) (*entity.Object, error)
	// ListObjectByIDs 主键批量查询（列表出 URL 用，禁止退化成逐行点查）
	ListObjectByIDs(ctx core.Context, ids []uint64) ([]*entity.Object, error)
	// CreateObject 建行；撞 uidx_object_store_md5 时由调用方重查复用赢家
	CreateObject(ctx core.Context, ent *entity.Object) (uint64, error)
	// ExistsObject 存在性判断
	ExistsObject(ctx core.Context, storeKeyword, md5 string) (bool, error)
	// IsReferenced 引用判定：SELECT 1 FROM file WHERE object_id=? LIMIT 1
	IsReferenced(ctx core.Context, objectID uint64) (bool, error)
	// DeleteObjectIfUnreferenced 回收：带 NOT EXISTS 的 CAS 删除（见 09-回收与后台任务）
	DeleteObjectIfUnreferenced(ctx core.Context, objectID uint64) (bool, error)
	// ScanUnreferenced 离线核对：按主键区间分批扫零引用行
	ScanUnreferenced(ctx core.Context, afterID uint64, limit int) ([]*entity.Object, error)
}
```

`entity.Object` 的 `Size uint64`；`Ext` 可为空串。

## 2. 核心不变量

> **`object` 只服务写侧（去重判定）与回收侧（GC、离线核对），公共读一次库都不查。**

这是贯穿全局的架构主线的落点（见 `README.md` §1.1）：展示路径需要的信息全部在 URL 里。

## 3. 去重边界是 store，不是 app

真正决定"字节存在哪里、谁付成本、走哪个域名、在哪个区域"的是 store，`app` 只是"该往哪个 store 写"的配置来源。所以同一张图被 5 个 app 使用、而这 5 个 app 配同一个桶时，桶里是**一份**字节、`object` 是**一行**、URL 是**同一个**；不同桶各自一份是物理必然，不是重复。业务归属在 `file.app`。

## 4. 对象命名规则：`{md5}.{ext}`，一层平铺

**`md5` 指什么**：**不是整文件 MD5，而是"分片摘要的摘要"**——按服务端下发的 `chunkSize` 切片、逐片取 MD5、按片号拼成 hex 串后再取一次 MD5。完整定义与理由见 **06-upload §4.2**。本册只关心它的三个性质：**32 位小写 hex**、**由内容唯一决定**、**客户端算、服务端核**。

| 细则 | 内容 |
|---|---|
| 1 | **`md5` 一律小写**。摘要计算结果必须归一化成小写再入键，否则同一份字节以两种写法上传会得到两个对象 |
| 2 | **`ext` 归一化**：小写、仅 `[a-z0-9]`、不含点、写入前校验长度（列宽 16）。清洗后不合法就落空串，不允许猜 |
| 3 | **`ext` 为空串时对象名退化为 `{md5}`**。因此**任何解析对象名的代码都不得用"固定段数"判定**，必须用 `filepath.Ext` 这一个入口 |
| 4 | **秒传命中即复用行，绝不复写 `ext`**。后缀是首写者的事实；复写会改对象名，而对象名在公网 URL 里，改了就是打断所有已发出的历史外链 |
| 5 | **显示与下载一律以 `file.name` 为准**，`object.ext` 只是外观 |

构造与解析**只能走 `pkg/objectkey`**（唯一入口，见 01-基础设施 §5）。

### 4.1 为什么不带桶段、不带日期分层

- **不带桶名 / store 段**：桶已由 `store_keyword` 确定，把桶名写进同一个桶里的对象名是自我指涉。store 的定位信息由 **URL 的 host**（`public_base_url`）承担，不进键。
- **不带日期或哈希分层**（`{app}/2026/10/{md5}` 这类）：厂商本身按 key 哈希分区，不需要手工分层；更硬的理由是**键里一旦出现时间成分，它就不再能由 `(store_keyword, md5, ext)` 推导**，那就必须把 `object_key` 存进表——"不存键"和"日期分层"这两个选择互斥。

## 5. 重复上传是幂等覆盖，不是冲突

键由内容决定 ⇒ 同桶同字节的 PUT 落在同一个对象上，覆盖无害。唯一有害的情形是"同 md5 不同字节"（碰撞或客户端报错值），它会静默覆盖掉别处引用指向的对象——所以写前的唯一索引查询命中后**必须比对 `size`**，不一致直接拒绝。这是内容寻址命名下唯一的护栏。

## 6. `size` 两层校验

| 层 | 位置 | 比对 |
|---|---|---|
| **写入层** | 真实上传字节的路径 | **实际收到的字节数 == 请求声明的 `size`**（直传路径一律用 `ListParts` 各片 `Size` 之和——字节客户端直传厂商、服务端看不到原文，见 06-upload §5）。不符即拒绝，不入 `object` 行、不返回 Key |
| **秒传层** | 命中已有对象 | **请求声明的 `size` == `object.size`**。因为第 1 层，此处是"客户端声明 vs **服务端事实**" |

**第 1 层的作用是保证 `object.size` 永远是服务端证实过的事实**，而不是首写者的声明。缺了这一层，第 2 层就退化成"两个客户端声明互相比对"。

**为什么单位不能退回 KB**（那样 32 位能到 4 TB）：两层校验是"**实际收到的字节数 == 请求声明的 `size`**"的精确比对。KB 只能声明取整值——一个 1025 字节的文件，声明 1 KB（1024）或 2 KB（2048）都对不上 1025；要让它成立就得在两处各加一套取整规则，且方向必须逐字一致，失配表现为**随机拒绝上传**。所以 API 的 `size` 是**字节**，且 proto 侧必须是 `string`（见 10-接口契约）。

**`size` 之外还有一条摘要核验**（06-upload §4.2、§5.1、§7.1 判据 4）：服务端在**对象诞生之前**重算 `md5`，不符即中止。两条的分工是——`size` 管"多大"，摘要管"是哪一份"。**只靠 `size` 封不住"同 `md5` 不同字节"**：一份 1024 字节的文件完全可以被另一份 1024 字节的文件冒充，`size` 比对对此一无所知。

### 6.1 残留风险（显式接受）

**先说清这条校验能挡什么、不能挡什么**：

- **能挡**：误命中与碰撞——客户端声明一个 `(md5, size)`，若大小对不上库里的行，直接拒绝。这是它的全部作用。
- **不能挡**：一个**手握真实字节**的攻击者。他拿目标文件算出真实的 `md5` 与 `size`，声明上去就能命中秒传、拿到 URL——但这**不是新获得的权限**：对象键是 `{md5}.{ext}`、URL 公开可读（§2 与 `SQL设计.md` 的"公有读 = 无访问控制"），**任何拿到过这份文件的人本来就能自己算出 URL**。"秒传让攻击者拿到 URL"这个说法是错的——秒传没有多给他任何东西。

**真正要防的是"同 `md5` 不同字节"**，即有人拿某个 `md5` 对应的键去装**别的**内容。这条由 **06-upload §4.2 的摘要核验** + 本册写入层 `size` 校验共同封死：直传路径（含 `chunkCount=1` 的单片）在对象诞生之前重算摘要，不符即中止 ⇒ 桶里不会出现"挂着别人摘要"的字节；秒传路径**一个字节都不写** ⇒ 它不可能污染任何键。

因此**"已入库即不可变"才是这个设计真正在守的东西**：`size` 比对不是防攻击者的护栏，而是"同一 `md5` ⇒ 同一份内容"这条等价的**廉价实现**——MD5 碰撞在现实中不可构造，唯一现实的偏差来源是客户端报错值或传错文件，而那时大小几乎总是对不上。

**因此不需要 PoP**：证明持有（PoP，随机 range 挑战）只能证明"你手上确实有这份字节"，它**证不了"你声明的 `md5` 等于这份字节的摘要"**——攻击者手里就是有 M，你出什么 range 他都能答。PoP 防的是"没有内容却要拿 URL"，而这里的前提恰恰是攻击者**已经有内容**。**唯一能真正封住的是服务端重算摘要**，也就是 06-upload §4.2 已经落地的那件事。**早先"引入 PoP 或取消秒传"的表述是方向错的，作废。**

## 7. 一条必须守住的不变量

> **内容不能落到不由上传方控制的桶里。**

所以去重查询的作用域必须是"上传方 app 当前配置的 store"，**禁止**全表按 md5 找。少了这一步就会出现"B 上传的图秒传成功、内容实际躺在 A 的桶和 A 的域名下"——成本、区域、外链归属全部错位，而排查时看不出任何异常。

## 8. 读路径以 `object` 为准，不以 `app_config` 为准

`app_config.store_keyword` 是"现在写去哪"，`object.store_keyword` 是"当时写去了哪"。混用的后果是 app 一换桶，所有历史图片链接立刻断。这也是要求外部存**完整 URL**（含 host）而不是裸对象名的原因——裸对象名没有 host，就只能拿当前配置去猜历史位置。
