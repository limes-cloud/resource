## 1. 仓储接口

```go
// repository/app_config.go
type AppConfig interface {
	// GetAppConfig 读配置：Redis 优先；miss 时抢锁回源并回填（见 §3）
	GetAppConfig(ctx core.Context, app string) (*entity.AppConfig, error)
	// ListAppConfig 分页查询
	ListAppConfig(ctx core.Context, req *types.ListAppConfigRequest) ([]*entity.AppConfig, uint32, error)
	// CreateAppConfig 新建（**不删缓存**，见 §6.4）
	CreateAppConfig(ctx core.Context, ent *entity.AppConfig) (uint64, error)
	// UpdateAppConfig 更新行并执行延迟双删（写动词自带失效，见 §6.2）
	UpdateAppConfig(ctx core.Context, ent *entity.AppConfig) error
}
```

**没有 `Delete`**（2026-10-13 16:33 定）：与 `store` 同立场——`app_config` 是**被数据面引用的配置行**（`status` 是上传闸门、`store_keyword` 是写入落桶的依据），删掉会让历史行为无法解释。下线一个 app = `status=0`，**走 `UpdateAppConfig`**，因此自动带上延迟双删（见 §6.5 第 2 条）。DB 拦不住 `DELETE`，只能靠"接口上根本没有那个入口"兑现——与 `store` 的"行只增不减"同一条思路。

**没有 `Invalidate`**（2026-10-13 定）：缓存只被两类动作触碰——**写路径删、读路径回填**。既然删只发生在 `Update`（本表无 `Delete`，见上），而它就在 infra 之下，接口上就不该再暴露一个"谁都能调"的删缓存方法。理由与命名冲突见 §6.2。

`entity.AppConfig` 的 `ExportStoreKeyword string`：**必填、不为空**（导出产物的落桶，见 08-导出）。2026-10-14 改：原设计为 `*string`、NULL = 回落 `StoreKeyword`，现改为必填的独立字段，不再回落。

## 2. 缓存载体与口径

| 项 | 值 |
|---|---|
| key | `resource:app_config:{app}` |
| value | **整行快照**（不是只缓存 `temp_url_ttl`） |
| TTL | 1 小时（兜底） |
| 负缓存 | 空结果 10s（挡穿透）；**与正缓存同 key、用哨兵值区分**（2026-10-13 16:33 定，见 §6.5） |
| 重建锁 | `resource:lock:app_config:{app}`，`SET NX PX 3000`；**只用于防击穿**，不承担正确性（见 §6.3） |
| **写路径**（仅 `Update`——本表不提供 `Delete`，见 §1） | **只删、不写**：更新行 → 删 key → 延迟 500ms → 再删一次 |
| **读路径**（`Get`） | **只拉、不删**：miss → 抢重建锁 → 双检 → 查库 → 回填 → 放锁 |

**协议只有这两个动作**（2026-10-13 定）：写路径永不回填、读路径永不删除。这条对称性把"缓存里为什么是这个值"收敛成两个可枚举的来源——要么是某次读的查库结果，要么什么都不是。任何"写完顺手刷一下缓存"的写法都会引入第三个来源，而它**没有对应的失效动作**（刷错了谁负责删？），是本设计明确禁止的。

**为什么缓存整行而不是只缓存 `temp_url_ttl`**：写路径（`store_keyword` / `status`）读的是同一份，省一次点查；更重要的是只有一份快照，不会出现"同一次请求里 TTL 是新值、`store_keyword` 是旧值"的撕裂。

**读**：`GET` 命中即用（**命中时 0 次 DB 查询**）；未命中 → 抢锁 → 双检（可能已被别人回填）→ 查库（走 `uidx_app_config_app`）→ 回填（带 TTL 兜底）→ 放锁。查库也无行 → 回填**空结果哨兵**（10s），按"app 未配置"处理，**不懒创建、不回落服务级默认**。

**三道保护各挡一件事**，不要混：

| 现象 | 机制 |
|---|---|
| 穿透（反复查不存在的 app） | 负缓存 10s |
| 击穿（热点 key 失效瞬间的并发回源） | 重建锁 |
| 雪崩（大批 key 同时失效） | 不存在：key 按 app 分散、TTL 无批量对齐 |

## 3. 缓存协议的执行

执行细节（`ctx.Clone()` 起 goroutine、500ms 代码常量、Redis 读写与锁原语）在 **01-基础设施「`infra/dbs/cache.go`」**。本册只讲与 `app_config` 绑定的部分。

### 3.1 写路径：延迟双删

**写**（`Update`）：更新行 → 删 `resource:app_config:{app}` → 延迟 500ms 再删一次。**写路径不回填**——它只负责让旧值消失。

**为什么必须做**：读路径 `GET` miss 时会**回源查库并回填**。若写路径只删一次，一个"在删之前就查了库、在删之后才回填"的并发读会把旧值重新塞回缓存，且此后无人清理（直到 TTL）。第二次删就是为这个窗口兜底。

**为什么是"延迟"而不是"立刻删两次"**：两次紧挨着的删之间没有时间差，中间那个并发读的"查库 → 回填"依然完整地发生在两次删之后 ⇒ 等于只删了一次。**延迟量必须覆盖"读请求从查库到回填"的最坏耗时**，500ms 是这个量的工程经验值（不做成配置项，理由见 11-配置）。

**一致性口径**：这是**最终一致 + TTL 兜底**，不是强一致。双删之后仍有极小概率的陈旧回填（读请求跨越两次删、且回填慢于延迟），概率低到可忽略，且 Redis TTL 会兜底。配置类数据的容忍度足够。

### 3.2 读路径：锁内回填

```
GET resource:app_config:{app}
  ├─ 命中 → 直接用（0 次 DB）
  └─ miss → SET resource:lock:app_config:{app} <token> NX PX 3000
        ├─ 抢到 → 再 GET 一次（双检，别人可能刚回填）
        │          ├─ 命中 → 直接用
        │          └─ 仍未命中 → 查库 → SET key（有行=整行快照 EX 3600；无行=哨兵 EX 10）
        │        → 释放锁（Lua 比对 token 后 DEL）
        └─ 没抢到 → 自旋重试 GET（20ms × 5，共 ~100ms）
                    └─ 仍未命中 → **直接查库返回，但绝不回填**
```

**四个必须写死的点**：

1. **抢到锁后要双检**。从 `miss` 到 `抢到锁` 之间，上一个持锁者可能已经回填完成。不双检就会做一次无谓的查库与回填。
2. **没抢到锁时，兜底直查但绝不回填**。兜底是为了"持锁者崩溃/卡住时不至于让请求挂死"；不回填是因为**绕过锁回填等于没有锁**——回填是唯一会写入缓存的读动作，必须收敛在锁内。
3. **释放锁必须比对 token**（Lua `if get(lock)==token then del(lock) end`）。否则持锁者超时后锁被 TTL 释放、又被别人抢到，原持锁者醒来一 `DEL` 就删掉了**别人的**锁，锁的保护瞬间归零。
4. **锁的失败模式是"退化为直查"，不是"拒绝服务"**。锁超时、Redis 抖动、持锁者崩溃——所有异常路径都收敛到"每个请求各查一次库"，正确性不受影响，只是回源次数变多。**这是它能被接受的前提**：一个不承担正确性的锁，坏了也不该影响正确性。

> 进程内并发可以在锁之前再叠一层 `singleflight` 把同一实例的并发合并掉（省掉大部分抢锁往返），它不改语义、只是省一次 Redis 往返。首版不做，留作优化位。

## 4. 为什么 `store` 不走 Redis、本表走

`store` 的 `keyword` 不可改、行只增不减，进程内启动加载最省且零网络跳；`app_config` 可变且**需要跨实例失效**，必须有共享载体承担"失效广播"。两者载体不同是刻意的。

> 注意"跨实例失效"与"延迟双删"是两件事：**跨实例**由共享的 Redis 承担（一次 `DEL` 对所有实例可见）；**延迟双删**解决的是同一个缓存上的**读-改-回填竞态**，与实例数无关。

## 5. 与下游的接口

- **05-object / 06-upload**：`store_keyword` 决定"现在写去哪"；`status=0` 时拒绝上传。**读路径以 `object.store_keyword` 为准**，不以本表为准——混用会让 app 一换桶、历史链接全断。
- **08-导出**：`export_ttl` 是产出物 TTL；`export_store_keyword` 解析导出落桶（**必填、不回落**）。
- **`temp_url_ttl`**：临时 URL 签名有效期。

## 6. 缓存协议定稿（2026-10-13 16:04 拍板）

**拍板内容**：延迟双删；**只删缓存**；**只在 `Update` / `Delete` 时删**；**`Get` 时由分布式锁拉入缓存**。

> **触发点的最终形态**（2026-10-13 16:33 定）：本表**不提供 `Delete`**（§1），所以"闭集 `{Update, Delete}`"在本表上**实际收敛为 `Update` 一个触发点**。拍板原话里的 `Delete` 保留为历史依据——将来若真加了删除接口，它自动落进同一闭集，无需重新论证。顺带消掉一条义务：本表既然没有删除动作，"删除路径也要记得失效"这条**根本不存在**（没有入口的操作不会被误做）。

### 6.1 这条拍板同时定了三件事

| # | 定了什么 | 依据 |
|---|---|---|
| 1 | **写路径与读路径的动作是对称且互斥的**：写只删、读只拉 | "只删缓存" + "Get 时拉入缓存" |
| 2 | **删除的触发点是闭集 `{Update, Delete}`**（本表实际只有 `Update`，见上注） | "只在 Update 和 Delete 时删除缓存" ⇒ `Create` **不删**，`Get` **不删**；本表不提供 `Delete`（§1）⇒ 收敛为单点 |
| 3 | **回填必须发生在锁内** | "由分布式锁拉入缓存" ⇒ 无锁回填 = 没有锁 |

第 1 条排除了一个常见但错误的写法：**写完顺手刷一下缓存**（write-through / refresh-after-write）。它给缓存引入了第三个值来源，而这个来源**没有对应的失效动作**——刷错了谁负责删？本设计里"缓存里为什么是这个值"必须能收敛成"某次读的查库结果"或"什么都没有"。

### 6.2 接口收口：删掉 `Invalidate`（原三选一里的方案 ①）

**为什么必须落在 infra**：`.claude/rules/domain-layer.md` 的 service 禁止事项第 1 条明令 **service 不得直接 import DB / Redis**。延迟双删本质是"对 Redis 删两次"，service 连 Redis 都拿不到 ⇒ 只能在 infra 之下。这一点无需讨论。

**为什么连接口都不暴露**：拍板第 2 条说删除的触发点是**闭集** `{Update, Delete}`，而这两个都是写动词、都在 infra 之下。于是 `Invalidate` 在领域层**没有任何合法调用方**——它唯一的作用就是给 service 开一个"自己删缓存"的口子，而 service 一旦能删缓存，就会出现"先删缓存再写库""写库失败但缓存已删"这类序列，infra 统一管理的意义被架空。**接口上不存在的动作，写不出来。**

**顺带解掉的重名**：`.claude/rules/infra-layer.md` 的方法命名表把 **`Invalidate` 分配给了"软删除（设置 `valid_to`）"**（`:37`；实现见 `:115` 的 `Memory.Invalidate`，对应的 repository 接口 `InvalidateMemory` 在 `domain-layer.md:117`）。而**同一个文件**里又有一个 `InvalidateWindowCache`（`:242`）= Redis `DEL`。也就是说 `Invalidate` 这个词**在同一个文件内部就指两个量**——只看方法名无法判断是"软删行"还是"删缓存"。所以 `infra/dbs/cache.go` 的删除原语**不叫** `Invalidate`，叫 **`ClearCache`**（2026-10-13 定）。

> **诚实标注**：本项目**不用软删除**（README §1 边界表："表哲学是'行在即活'；需要下线的配置对象用 `status=0`，不做软删标记"），所以"软删行 vs 删缓存"这个歧义在本项目里**不会被实际触发**——它**不是缺陷，只是命名卫生**。改名成本为零，故照改；不要把这条当成 bug 记录。

**配套义务：写动词不得被 `ctx.Transaction()` 包裹。** 这不是洁癖，理由分两种情形，严重程度差一个量级：

| 情形 | 时序 | 后果 |
|---|---|---|
| **A. 第一次删早于 commit** | `DEL`(t=0) → 并发读回填旧值 → `DEL`#2(t=500ms) → `COMMIT`(t=300ms，快事务) | **可自愈**：`DEL`#2 在 commit 之后，把旧值清掉 |
| **B. 第二次删也早于 commit** | `DEL`(t=0) → `DEL`#2(t=500ms) → 并发读回填旧值(t=600ms) → `COMMIT`(t=800ms，慢事务/等锁) | **不可自愈**：两次删都用完了，缓存持旧值直到 **1h TTL** |

情形 B 的触发条件是**事务耗时超过 500ms**（等锁、慢盘、批量写）。它把"最终一致"退化成"最多 1 小时不一致"，而 `app_config.status=0` 是**上传闸门**——已停用的 app 会在这段时间里继续被允许上传。`app_config` 是**单行写、无跨表原子需求**，本来就不需要事务 ⇒ 定一条义务"写动词不得被事务包裹"，即可保证"方法返回 == 已提交"、方法内的失效天然 post-commit。

> **⚠️ 重建锁不能替代这条义务。** 加了分布式锁之后情形 B **依然存在**：B 里的每个读请求都在锁内被正确串行化了，但它们读到的**确实是**旧数据（写事务尚未提交，任何隔离级别下都读不到新值）——锁解决的是"并发"，不是"可见性"。两者是正交的。若将来确实要把某个写动词包进事务，**第二次删必须挂在 commit 之后**（提交回调里排期），不能从方法内部排期；"延迟 500ms"给不出与事务耗时的关系上界。

### 6.3 与「全服务不使用分布式锁」的关系：措辞要收窄

01-基础设施 §8.2 现在写的是"**全服务不使用分布式锁**"。这条拍板引入了一把锁（读路径的重建锁），所以那句话必须收窄——**不是推翻，是把范围说准**：

| 锁的用途 | 承担什么 | 本设计 |
|---|---|---|
| **数据面竞态**（谁领任务、谁建行、谁删对象） | **正确性**——错了会丢数据/重复执行 | **一律不用锁**，乐观 CAS + 唯一索引全覆盖 |
| **缓存重建**（谁去查库回填） | **成本**——错了只是多查几次库 | 用锁（本册） |

判据是**"这把锁坏掉时会怎样"**：数据面的锁坏掉 ⇒ 数据错；重建锁坏掉 ⇒ 每个请求各查一次库，**正确性分毫不差**。所以 §8.2 的原话应改为"**数据面竞态不使用分布式锁**"，并把重建锁登记为不承担正确性的锁（见 01-基础设施 §8.2）。原话里"加锁会引入新的失败模式（锁超时、锁泄漏）"依然成立，但那些失败模式在重建锁上的后果是**可接受的退化**，不是事故。

> **补充（2026-10-13 16:55）**：§8.2 现在写的是**两把**非正确性锁——重建锁之外又添了**导出任务亲和锁**（08-导出 §7.1，坏了退化为全局 claim）。当时那句"唯一例外"已作废。**判据没变**，只是"成本"这一档现在有两个成员。

### 6.4 显式接受的代价：`Create` 的 10s 窗口

拍板第 2 条把 `Create` 排除在删除触发点之外，因此**新建配置后，负缓存（10s）会继续把该 app 当"未配置"**——最多 10s 内 `GetAppConfig` 直接返回 not found，不回源。这是"触发点是闭集"的直接代价，**当前显式接受**。

理由是量级：`CreateAppConfig` 是**应用接入**动作（低频、管理侧驱动），10s 的配置传播延迟对"刚接入就立刻跑流量"的场景无害。**但它是一个真实的行为承诺，必须写下来**——否则会被当成 bug 排查。

若要缩短这个窗口，只有三条路，各自有代价：

| 做法 | 代价 |
|---|---|
| `Create` 也删缓存（破例） | 破坏"触发点是闭集"这条干净规则；且 `Create` 通常**没有旧值可删**，双删的第二次纯属浪费 |
| 负缓存 TTL 缩短到 1s | 穿透保护变弱；且没解决根因，只是把窗口调小 |
| **取消负缓存** | 穿透改由重建锁兜（同一 app 的重复查询被锁合并）⇒ 代价可接受，但每次 miss 都要抢锁（多一次 Redis 往返） |

**当前选"接受 10s"**。若将来接入流程改成"配置先建、流量后放"（这是更常见的顺序），窗口自动消失。

### 6.5 两个小项已定稿（2026-10-13 16:33）

1. **负缓存与正缓存用同一个 key**（**已定**）。同一个 `resource:app_config:{app}` 里存两种值：查库有行 ⇒ **整行快照**（`EX 3600`）；查库无行 ⇒ **哨兵值**（`EX 10`）。
   - 好处：**一次 `DEL` 同时清掉正/负两种状态**，写路径不需要记得"删两个 key"——少一条"漏做无现象"的义务；也与"一个量只有一个名字"同源（一条 app 的配置状态收敛成一个键）。
   - 实现上最省的做法是**空串即哨兵**：`SET key "" EX 10`。读时 `GET` 返回 `nil`（Redis 空回复）= 真 miss ⇒ 抢锁回源；返回 `""` = 已知不存在 ⇒ 直接按"app 未配置"返回、**不抢锁**；返回 JSON = 命中 ⇒ 直接用。三者天然可区分，**不需要另造一个"哨兵串"常量**。
   - 代价：脏值（解析失败）一律按 miss 处理——抢锁回源会自愈，不会把缓存变成一堵墙。

2. **`app_config` 不提供 `Delete`**（**已定**）。与 `store` 同立场：`app_config` 是**被数据面引用的配置行**（`status` 是上传闸门、`store_keyword` 是写入落桶的依据），删掉会让历史行为无法解释。下线一个 app = `status=0`，**走 `UpdateAppConfig`**，因此自动带上延迟双删。

   > **前提**：下线必须走写动词，**不能是一条裸 `UPDATE`**——裸 `UPDATE` 绕过延迟双删，被下线的 app 会在缓存里继续以 `status=1` 存活到 TTL。而 `status=0` 是上传闸门 ⇒ 等于闸门在 TTL 内失效（与 §6.2 情形 B 的后果同型）。
   >
   > 这条同时让 §6.1 第 2 条的"闭集"在本表上收敛为单点，并让 `README.md` §3 遗留第 1 条**结案**（连带更新：`README.md` 决策 D2、`10-接口契约.md` 服务清单、`01-基础设施.md` §4.2、`.prd/SQL设计.md` 第 2 节）。

**已明确、无需再议**：延迟删 goroutine 必须 `ctx.Clone()`；进程关闭时在飞的第二次删会丢——因第一次删已发生 + Redis TTL 1h 兜底 ⇒ **显式接受**。
