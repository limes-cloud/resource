## 1. 目标与范围

### 1.1 服务定位

`resource` 是一个**多租户静态资源中心**，为上层业务提供四件事：

| 能力 | 说明 |
|---|---|
| **文件托管** | 目录树 + 文件条目；字节落对象存储，元数据落 MySQL |
| **上传通道** | 秒传（内容寻址去重）、多段直传（全部**客户端直传厂商**，含 `chunkCount=1` 的单片，断点续传） |
| **公网分发** | 对象公网可读，URL 由 `{public_base_url}/{对象名}` 拼出；读路径不经过服务 |
| ~导出~ | 按规格异步生产 zip/xlsx 产物，TTL 驱动回收 |

> **⏸ 范围声明（2026-10-13 定）：导出功能整体首版不实现。** 08-导出 全册、`SQL设计.md` 第 7 节两张表、09 中五条导出任务线、10 的 `ExportService`、11 的 `business.export` 配置段**设计保持定稿**（作为后续实现依据），但实现推迟到首版之后；连带延后的还有第 9 条的容量调度与本地目录草稿（`.prd/草案-导出本地目录与容量调度.md`）。首版范围 = 文件托管 + 上传通道 + 公网分发 + 配置面 + upload GC / 离线对象核对两条后台线。实现时机另行启动，启动时先处理 README §3 遗留表里标记"随导出延后"的条目（9、11）。

**一条贯穿全局的架构主线**：

> **展示路径需要的信息全部在 URL 里，`object` 表只服务写侧（去重判定）与回收侧（GC、核对）。公共读一次库都不查。**

这条不变式决定了后面几乎所有的取舍——去重边界是 store、键不含桶段与日期段、`size` 必须服务端证实、`app_config` 必须走缓存。

### 1.2 设计目标

| # | 目标 | 落地方式 |
|---|---|---|
| G1 | **写路径可推导，不存第二份真相** | 对象键由 `(md5, ext)` 推导（`md5` = 按服务端下发的 `chunkSize` 切片、逐片摘要再汇总）；URL 由 store 配置推导；片数由公式推导 |
| G2 | **并发不加锁** | 乐观 CAS + 唯一索引覆盖全部竞态点（01-基础设施「事务与并发约定」） |
| G3 | **读路径零查询** | store 走进程内全量 map；`app_config` 走 Redis；公网读不经过服务 |
| G4 | **失败方向明确** | 所有残留按"宁可留孤儿，不可留悬空行"取舍（01-基础设施「并发语义总原则」） |
| G5 | **约束显式化** | DDL 只留 PK/UNIQUE；值域与引用由服务层校验 + 启动自检兜底（12-工程与交付） |
| G6 | **跨层口径唯一** | 单位、字符集、类型、命名各有一份权威表（01-基础设施、10-接口契约） |

### 1.3 边界：不做什么

| 不做 | 理由 |
|---|---|
| 对象级访问控制 / ACL | 与内容寻址互斥——键由内容唯一决定，知道内容的人就能推出键。需要访问控制的场景由 `cdn_auth_type` 的签名 URL 承担 |
| 图片处理（缩放、水印、格式转换） | 由接入方 / CDN 侧承担；服务不拼参数（顺带避开"CDN 缓存 key 不含 query ⇒ 所有尺寸命中同一份缓存、静默返回错图"这个服务控不了的坑） |
| 配额（`quota_bytes` / `used_bytes`） | 用量是可汇总的派生值；事务内计数器一旦与事实表不一致就再无可信度 |
| 引用计数（`ref_count`） | 同上；回收走扫描（`SELECT 1 FROM ... LIMIT 1`），低频路径多一次索引查询不是成本 |
| 软删除 | 表哲学是"行在即活"；需要下线的配置对象用 `status=0`，不做软删标记 |
| MySQL 8.0 专属语法 | 不用 CTE、窗口函数、`utf8mb4_0900_*`；全库表级排序规则 `utf8mb4_unicode_ci` |
| 上传数据面（上传字节） | 全部由**客户端直传厂商**（D16，2026-10-13 改）。服务端只做控制面——转发任何文件都等于把出网带宽与长连接都压在自己身上；统一直传后，核验全部在 `CompleteMultipartUpload` 之前用 `ListParts` 的 ETag 完成（含 `chunkCount=1` 的单片） |
| 分布式锁（**数据面**） | 乐观 CAS 已覆盖全部竞态点；加锁会引入锁超时、锁泄漏等新失败模式。**两处例外都不承担正确性**：缓存重建锁（坏了退化为直查，见 D2）与导出任务亲和锁（坏了退化为全局 claim，见 D13）——01-基础设施 §8.2 |
| 向后兼容 | 本文档定义的是一份新契约，不做双写、不做灰度兼容层 |

## 2. 关键设计决策一览

这张表是全文索引，每条都能在 SQL 设计里找到对应论证。

| # | 决策 | 落点 |
|---|---|---|
| D1 | 配置面进 DB、进程内全量 map；`store` 只增不减、只 `status=0` | 02-store、12-工程与交付 |
| D2 | `app_config` 缓存协议：**写路径（`Update`）只做延迟双删、读路径（`Get`）在分布式锁内回填**；命中 0 次 DB。**正/负缓存同 key**（空串即哨兵）；**本表不提供 `Delete`**，下线 = `status=0` 走 `Update` | 03-app_config |
| D3 | 目录用物化路径，无 `parent_id`，限深 10 | 04-directory |
| D4 | 对象键 `{md5}.{ext}`，去重边界是 store 不是 app | 05-object |
| D5 | `size` 两层校验（写入层 = 服务端事实；秒传层 = 声明 vs 事实）+ **摘要核验**（服务端在对象诞生之前重算 `md5`，不符即中止、不留对象） | 05-object、06-upload |
| D6 | `chunkSize` 全整数推导，服务端**经取片大小接口**下发（客户端据此算 `md5`），不进任何表 | 06-upload |
| D7 | `upload` 只有活跃会话；完成事务 = 建 object + 建 file + 删会话；**同 (store, md5, user_id, directory_id) 只有一个在飞会话（`uidx_upload_session`），续传 = 重调 Prepare 召回，客户端无需保存 uploadId** | 06-upload |
| D8 | 导出拆 `export_task`（产出物，TTL 驱动）与 `export`（请求记录） | 08-导出 |
| D9 | 导出重试靠乐观 CAS + `leased_at` 租约心跳 / `failed_at` 退避起点，无锁、无 `next_retry_at` | 08-导出 |
| D10 | 对象回收 = `A − B` 集合差，宁可留孤儿不可留悬空行 | 09-回收与后台任务 |
| D11 | 启动自检只覆盖配置面，数据面引用靠写入路径 | 12-工程与交付 |
| D12 | proto 只 `size` 是 `string`，其余 64 位一律 `uint32` | 10-接口契约 |
| D13 | **支持多实例部署**：七个后台任务无需选主（各自 CAS / 唯一键仲裁 / 谓词幂等）；导出 worker 靠**创建时拿锁的任务亲和**（锁 TTL = `lease`，实例挂掉即自然移交） | 08-导出、09-回收与后台任务、12-工程与交付 |
| D14 | 时间列分**审计**（`created_at`/`updated_at`，GORM 自动）与**计时**（`leased_at`/`failed_at`/`upload.updated_at`，代码显式写）两类，不许混用 | 01-基础设施 |
| D15 | 内容摘要 `md5` = **分片摘要的摘要**（按 `chunkSize` 切片 → 逐片 md5 → 按片号拼 hex 串 → 再取 md5；单片 N=1 同规）；**客户端算、服务端在对象诞生之前核**。因此 `chunkSize` 公式升为**协议契约**——改它等于改所有对象的键 | 06-upload、05-object、01-基础设施 |
| D16 | **字节流向：全部直传厂商**（含 `chunkCount=1` 的单片，2026-10-13 改）。服务端只发预签名分片 URL，按批取。直传的代价是摘要核验依赖"分片 ETag == 内容 MD5" ⇒ 用**能力位 + 启动自检**兜住（被引用的 store 不满足就**拒绝启动**） | 06-upload、10-接口契约、11-配置、12-工程与交付 |
