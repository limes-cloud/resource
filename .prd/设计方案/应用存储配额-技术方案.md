# 应用存储配额 — 技术方案

> 状态：待确认 ｜ 范围：server/resource + web/admin-web
> 已确认决策：**逻辑累加**计量（不管 sha 去重）· 导出产物**不计入** · 超限**硬拒** · 默认 **50G** · `0 = 不限` · 前端 **GB** 录入 / 后端存**字节**

## 1. 背景与目标

多应用共用 resource 服务上传文件，目前无总量约束，单应用可无限占用底层对象存储。给每个 `app_config` 配一个存储配额（默认 50G），用量累加到上限后**拒绝新上传**，存量文件仍可读可删。

**非目标**：不做软配额/告警分级、不做跨应用全局配额、导出产物（export_store）不纳入本配额。

## 2. 计量口径（关键）

- **逻辑累加**：`used_bytes = Σ(该 app 的每个 file 行所引用 object 的 size)`。同一内容被多个 file 行秒传复用时**逐行计**，不因物理去重而少算——与 sha 去重解耦，应用间隔离、计费直观。
- 单位：后端一律**字节**（`uint64`）；前端按 **GB** 录入展示（`bytes = GB * 1024³`）。
- `quota = 0` 表示**不限**（跳过一切校验）。

## 3. 数据模型

`app_config` 增两列：

| 列 | 类型 | 说明 |
|---|---|---|
| `quota` | `BIGINT UNSIGNED NOT NULL DEFAULT 0` | 配额上限（字节）；`0`=不限 |
| `used_bytes` | `BIGINT UNSIGNED NOT NULL DEFAULT 0` | 已用量（字节），账务维护 |

DDL（migration）：
```sql
ALTER TABLE app_config
  ADD COLUMN quota      BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '存储配额(字节),0=不限',
  ADD COLUMN used_bytes BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '已用量(字节)';
```

entity（`internal/domain/entity/app_config.go`）新增：
```go
Quota     uint64 `json:"quota"     gorm:"column:quota"`      // 配额上限(字节);0=不限
UsedBytes uint64 `json:"usedBytes" gorm:"column:used_bytes"` // 已用量(字节)
```
> `quota`/`used_bytes` 合法值含 0 但语义是「累加/上限」，非「更新开关」，用值类型即可；只通过**原子表达式**更新（见 §5），不走 `Updates(struct)` 的零值跳过逻辑。

## 4. 写入链路：两个创建点都要管

`file` 行有**两个创建入口**，配额校验 + 用量累加必须两处都覆盖（否则秒传绕过配额）：

| 入口 | 代码位置 | 场景 |
|---|---|---|
| 秒传 | `Upload.PrepareUploadFile` → `finishFile`（`upload.go:106`） | `(store,md5)` 命中 object，直接建 file 行 |
| 正常完成 | `Upload.CompleteUpload` → `completeTransaction`（`upload.go:451`） | 合并分片后建 object + file 行；`GarbageCollect` 自动完成也走这里 |

两者最终都建 file 行；`completeTransaction` 已在事务内，`finishFile` 需要包进事务。统一在**建 file 行的同一事务**内做「校验 + 自增」。

## 5. 强约束：一条 CAS 语句既校验又占用（防并发）

核心是一条原子 UPDATE（repo 新增 `ReserveQuota`），放在建 file 行的事务里、`CreateFile` **之前**：

```sql
UPDATE app_config
   SET used_bytes = used_bytes + :size
 WHERE app = :app
   AND (quota = 0 OR used_bytes + :size <= quota);
```
- 影响行数 `=1` → 占用成功，继续建 file 行。
- 影响行数 `=0` → 已超限（或 app 不存在）→ 返回 `QuotaExceededError`，事务回滚。

单语句「检查+预留」合一，天然防住「两个并发上传各自预检都过、合起来超限」——这就是「超了就不超」的权威执行点。不读旧值再判断（那是竞态根源）。

**幂等防重复计**：`completeTransaction` 有重放分支（按 `upload_id` 命中已存在 file 行则复用、不新建）。`used_bytes` **只在真正新建 file 行时自增一次**；重放复用 / `isDuplicate` 命中既有行的路径**不自增**。`finishFile` 秒传同理，只在新建行时自增。

## 6. 预检（快速失败，非权威）

`PrepareUploadFile` 在建会话 / 秒传建行**之前**加一道软预检：读 `app_config`，`quota>0 && used_bytes + req.Size > quota` → 直接返回 `QuotaExceededError`。作用是省掉「传完分片才在 complete 被拒」的浪费；**权威仍是 §5 的 CAS**（预检与 complete 之间存在时间窗，并发下由 CAS 兜底）。

## 7. 删除回收

`File.DeleteFile`（`file.go:112`）已在事务内删 file 行 + 零引用删 object。于**同一事务**追加归还：
```sql
UPDATE app_config
   SET used_bytes = IF(used_bytes >= :size, used_bytes - :size, 0)
 WHERE app = :app;
```
按被删 file 行引用的 object.size 归还；`IF(...>=)` 防下溢到负（账务漂移时的护栏）。

## 8. 重算对账

`used_bytes` 是维护量，可能因异常（崩溃于「写桶成功、落库失败」之间、历史 bug）漂移。提供重算，按逻辑口径从明细回算：
```sql
UPDATE app_config a
   SET a.used_bytes = (
     SELECT COALESCE(SUM(o.size), 0)
       FROM file f JOIN object o ON o.id = f.object_id
      WHERE f.app = a.app
   );
```
入口：service 方法 `RecalcUsage(ctx, app)` / `RecalcAllUsage(ctx)`，暴露为内部接口（如 `POST /v1/resource/app-config/recalc`，受 `resource:appConfig:update` 控制），不进基础接口白名单。初期可只提供手动触发，不排期自动对账。

## 9. 存量回填

迁移加完列后（默认都是 0），对已有 app 跑一次 §8 的重算把 `used_bytes` 补齐；`quota` 存量默认 0（不限），由管理员按需逐个设置——**不批量塞 50G**，避免给存量应用凭空套上限。50G 仅作为**新建**配置的表单默认值。

## 10. Proto / API 变更

`api/app_config/proto/app_config.proto`：
- `CreateAppConfigRequest`：加 `optional uint64 quota`（字节；不传 = 后端默认，建议后端对 create 缺省 50G 或由前端始终传）。
- `UpdateAppConfigRequest`：加 `optional uint64 quota`（局部更新，不传=不改）。
- `AppConfigView`（响应）：加 `uint64 quota` + `uint64 used_bytes`（**只读**，前端展示容量条）。
- `used_bytes` 永不接受前端写入（Create/Update 请求里没有该字段），只在响应回显。

重新 `kratosx proto client api/app_config/proto/app_config_service.proto` 生成。

错误码 `api/errors/proto/errors.proto` 新增：
```
QuotaExceededError = <n> [(errors.message)="存储配额已满"];
```
HTTP 建议 403/400 档（按现有 errors 风格定），生成 `errors.QuotaExceededError()` / `IsQuotaExceededError()`。

## 11. 前端（web/admin-web）

- `api/resource/app_config/type.ts`：`AppConfigView` 加 `quota: number`、`used_bytes: number`；`CreateAppConfigRequest`/`UpdateAppConfigRequest` 加 `quota?: number`。
- 表单（`app-config/index.vue` `formItems`）：加「存储配额(GB)」`number` 项，默认 **50**，`min: 0`，tip「0 = 不限」；提交时 `GB → bytes`（`*1024³`），回填时 `bytes → GB`。
- 卡片（§对象存储卡片同款机箱）：底部/规格区加**容量条** `used/quota`，展示 `已用 32.1 / 50 GB · 64%`，接近满(≥90%)转警告色、`quota=0` 显示「不限」。这正好把之前预览里的「遥测条」落成真实字段。
- 列表接口 `ListAppConfig` 已返回整行，带上新字段即可，无需额外请求。

## 12. 边界与风险

- **秒传不绕过**：§4 两入口都过 §5 CAS，已覆盖。
- **重放不重复计**：§5 幂等约束，仅新建行自增。
- **写桶成功但落库失败**：file 行没建成 → 不占用（CAS 在事务内随之回滚）；桶里可能留悬垂对象，由既有 `GarbageCollect` 处理，与配额账无关。
- **并发删除/上传**：均为单行 `app_config` 的原子表达式更新，MySQL 行锁串行化，无需额外分布式锁。
- **漂移**：§8 重算兜底；`used_bytes` 用无符号 + 下溢护栏。
- **quota 调小到低于 used**：允许（存量不动、新上传一律拒），符合「超了就不超」。

## 13. 验证清单（接口级，起服务后打）

- 配额 50G、连续上传至接近上限：最后一笔使 `used+size>quota` 的上传在 **complete 被拒**（`QuotaExceededError`），桶内零新增、`used_bytes` 不变。
- **秒传**命中但会超限 → 在 `PrepareUploadFile` 被拒（覆盖秒传入口）。
- 两个并发上传各自预检都过、合计超限 → 其一在 CAS 处失败，`used_bytes` 不超 `quota`。
- 删除文件 → `used_bytes` 按 object.size 归还，不下溢。
- `quota=0` → 任意大小均放行。
- 重算接口：手动改脏 `used_bytes` 后调用，回到明细 SUM 值。
- `used_bytes` 不随 Update 请求被前端篡改；响应里始终回显权威值。

## 14. 回滚

- 代码回滚：移除 CAS/预检/归还调用即可，功能退化为「不限」。
- schema 回滚：`ALTER TABLE app_config DROP COLUMN quota, DROP COLUMN used_bytes;`（两列独立新增，无数据依赖，可安全 drop）。
- 分步可逆，无不可逆节点。
