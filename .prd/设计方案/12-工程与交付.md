## 1. 启动自检（承重墙）

DDL 里没有 CHECK、没有 FK，**唯一的兜底就是"启动时校验失败即拒绝启动"**。实现落在 `internal/initiator/selfcheck/`，在 `main()` 中于 `srv.App().Run()` 之前调用，失败即 `log.Fatal`。

```go
func main() {
	srv := core.InitApp(
		kratosx.WithRegistrarServer(app.Register),
		kratosx.WithValidateErrHook(...),
		kratosx.WithMiddleware(authorize.AuthMiddleware()),
	)

	ctx := core.MustContext(context.Background())
	selfcheck.MustRun(ctx)   // 失败即退出，不进入服务状态
	initmenu.Register(ctx)

	if err := srv.App().Run(); err != nil {
		log.Fatal(err)
	}
}
```

**自检项清单**：

| # | 检查 | 失败后果（若不做） |
|---|---|---|
| 1 | **全量加载 `store`（含 `status=0`）并逐个构造客户端** | 停用 store 名下存量对象整片 404 |
| 2 | `provider` 在白名单内 | 寻址方式推导不出来，静默用错寻址 |
| 3 | **`endpoint` 归一化断言**：`CanonicalEndpoint(provider, endpoint) == endpoint` | 归一化规则演进后，旧行与新行重新分裂成两行（**纯代码变更、DB 无感知**） |
| 4 | `app_config.store_keyword` / `export_store_keyword` 指向的 keyword 存在 | 孤儿引用只会在第一个上传请求时才暴露 |
| 5 | `public_base_url` 之间**不得前缀包含** | 按 URL 反解 store 的最长前缀匹配会把它判给错误的桶，表现为图片 404 或串成别人的图 |
| 6 | 四元组自洽：`endpoint` / `bucket` / `public_base_url` / `cdn_auth_type` | `s3_presign` 配 CDN 域名会让 SigV4 的 `host` 签名失效、整域 403；`cdn_a` 配厂商域名则没有执行方、`cdn_auth_key` 白配 |
| 7 | **分片 ETag 能力位**：该 `provider` 的分片 ETag **确实等于分片内容的 MD5**（即未开服务端加密） | 直传路径的**摘要核验会误拒所有上传（含 `chunkCount=1` 单片）**（用户可见、无自愈）——06-upload §4.2 |

**第 7 条的来历**（2026-10-13 定）：上传字节**客户端直传厂商**（06-upload §5，2026-10-13 改：含 `chunkCount=1` 单片）⇒ 服务端看不到原文，只能拿 `ListParts` 的分片 ETag 当"该片 md5"。**这是直传的代价，必须显式认下来**：不做的后果不是"少一层校验"，而是**正常上传全挂**。所以把它做成能力位 + 启动断言，**让它在启动时就炸，而不是在用户上传时静默误拒**。

**为什么第 5 条必须显式校验**：`https://cdn/a` 与 `https://cdn/a/b` 可以共存，但当某个 app 名恰好等于 `b` 时，前一个 store 里该 app 对象的 URL 与后一个 store 的前缀**完全同形**。等值已被唯一性挡住，前缀包含挡不住。

**明确不做**：`file.directory_id` / `file.object_id` / `export.task_id` 这类**数据面**引用**不做启动全量扫描**——这些表是亿级，扫不动，而它们的写入全部经过服务层（在事务内保证）。

## 2. 测试与验收

### 2.1 纯函数单测（必须锁死）

| 目标 | 用例要点 |
|---|---|
| `ObjectName` / `ParseObjectName` | 往返一致；`ext` 为空时退化 `{md5}`；**禁止按段数切分**——`a.b.c` 类名字必须用 `filepath.Ext` 得到 `c` |
| `ExportObjectName` | 恒为 `export/{md5}.zip` |
| `chunk.Size` / `chunk.Count` | 边界：`totalSize = 0`（EMPTY_FILE，直接拒绝、不进流程）/ `totalSize = 1` / 恰好 `5MB` / `10000 × 5MB`（恰好 5MB 片、10000 片）/ `10000 × 5MB + 1`（片数仍 ≤ 10000，**这是最容易错的跨分界点**）/ 42.94 TB 上界（返回 error 而非截断） |
| `chunk.Digest`（分片摘要的摘要） | **单片与分片必须同规**：同一份内容走单片（N=1）与走分片得到**同一个值**（否则去重与秒传同时失效）；拼接的是 **hex 文本**（**不是**二进制摘要 + `-N`）；乱序输入的 ETag 按片号升序归一；空输入报错 |
| `EscapeLike` / `PrefixPattern` | `\` / `%` / `_` 的转义顺序（先 `\`）；转义后仍是常量前缀 |
| `CanonicalEndpoint` | 四种拼写差异（域名族 / vhost / scheme / 尾斜杠）归一到同一值；归一化不出来时报错 |
| `exportMd5` | 覆盖 headers/rows/files(含 rename)/keys；**排除 name**（同内容不同名必须得到同一个 md5） |
| `AddressingStyle` | provider 白名单内外的行为；vhost-only 的例外区域 |

### 2.2 并发测试（CAS 与重建锁的验收点）

| 场景 | 期望 |
|---|---|
| 两 goroutine 同内容上传到同桶 | 一方赢、另一方复用赢家的 `object.id` 与 `ext`；只有一行 `object`；`size` 不符则拒绝 |
| 多 worker 并发 claim 同一任务 | 只有一次 `RowsAffected == 1` |
| **N 个并发 `GetAppConfig` 打同一个 miss key** | **只有 1 次回源查库**（重建锁生效）；其余或命中回填、或走兜底直查；**缓存里的值一定是查库结果**（没有任何绕过锁的写入） |
| **持锁者超时后另一请求抢到锁** | 原持锁者释放锁时**删不掉别人的锁**（Lua 比对 token）；若删掉了，说明释放逻辑退化成了裸 `DEL` |
| 心跳停摆超 `lease` 后跑租约恢复 | 该行变 `status=3` 且 **`failed_at` 被刷新为当前时刻**（若沿用旧值，下一轮会被立即重领，形成热循环） |
| 租约超时后原 worker 写成功 | `MarkSuccess` 的 `WHERE status=1` 不生效，不覆盖新状态 |
| 走一遍 claim → `MarkSuccess` | **`updated_at` 确实被 GORM 刷新**（`Updates(map)` 是否带了 `Model()`；这是 `SkipHooks` 回归的哨兵，改回 `UpdateColumn` 会让它静默不变） |
| 手动重试一条 `status=3` 的任务后立刻 `ListClaimable` | 该行出现在候选里，且其 `failed_at` 已是 `0`（复位后排在队首）；**同时断言不存在 `status=0 AND failed_at > 0` 的行**（不变式哨兵） |
| 请求一个已过期的产物（`status=2` 且 `expired_at<=now`，或 `status=4`） | 只 `INSERT export`，**任务行状态与计时列一律不变**（自动复活已撤销，无写路径与清理线相争）；重跑只能走手动重试，且 `expired_at` 一并复位为 `0` |
| 并发删共享同一 `object` 的不同引用 | 双方都保留（保守），留下零引用孤儿；**不产生悬空行** |
| 并发重放同一 `CompleteUpload` | `uidx_file_upload_id` 仲裁，只有一行 `file` |
| 同键并发 `PrepareUploadFile`（同 user / 同目录 / 同 `md5`） | `uidx_upload_session` 仲裁：只有一行 `upload`，撞键方**召回复用**赢家（返回其 `uploadId` + 已传片号），不新建会话；后续分片只补缺口 |
| 召回命中但厂商侧 `NoSuchUpload` | 删会话行、走新建，返回**新** `uploadId`（不得把死 `uploadId` 发给客户端） |
| 召回命中后重调 `GetUploadPartURLs` 只取缺失片 | 已传片不重复取址；`updated_at` 被顶（滑动续期生效，GC 不误杀） |
| **分片 ETag 序列与会话声明的 `md5` 不符** | 调 `AbortMultipartUpload`、**不调 `Complete`**、**不建 `object` 行**、桶里零残留（核验必须在 Complete 之前——顺序反了会覆盖掉键上的既有合法内容） |
| **上传声明的 `md5` 与 `ListParts` ETag 聚合值不符**（含 `chunkCount=1` 的单片） | 调 `AbortMultipartUpload`、**不调 `Complete`**、**不建 `object` 行**、桶里零残留（核验必须在 Complete 之前） |
| **取分片地址时 `partNumbers` 越界**（`0` / `chunkCount+1` / 超过批大小上界） | 拒绝，**不返回任何 URL**（与 §7.1 判据 1 同一口径） |
| 并发隐式建同名目录 | `INSERT IGNORE` + 重查，只有一行 `directory` |
| 手动重试撞上正在跑的 worker | `RowsAffected == 0`，返回"当前状态不可重试" |

### 2.3 契约测试

- proto 的 `size` 序列化为 **string**，`createdAt` / `total` 等序列化为 **number**（用 protojson 断言）。
- 时间戳 `uint32` 转换清单与代码实际转换点**逐条对齐**（10-接口契约 §2.1）。

### 2.4 启动自检的负例

对 §1 的七项各造一条非法数据，验证**拒绝启动**：

| 负例 | 期望 |
|---|---|
| `provider` 不在白名单 | 拒绝启动 |
| `endpoint` 未归一化（带 scheme / 带 vhost 前缀） | 拒绝启动 |
| `public_base_url` 存在前缀包含关系 | 拒绝启动 |
| `app_config.store_keyword` 指向不存在的 keyword | 拒绝启动 |
| `s3_presign` 配 CDN 域名 | 拒绝启动 |
| **被 `app_config` 引用的 store，其 provider 能力位 `partETagIsContentMD5 = false`**（例如开了服务端加密） | 拒绝启动 |
| `store.status = 0` 的行 | **必须正常加载**（这是反向用例：自检不能"只加载启用的"） |

## 3. 部署与运维

### 3.1 部署形态

**支持多实例部署**（2026-10-13 16:55 定）。七个后台任务**没有一条需要分布式选主**——逐条的凭据在 **09-回收与后台任务 §6.2** 的"多实例安全"列。**⏸ 首版范围（2026-10-13 定，README §1.1）**：导出首版不实现 ⇒ 只上线 **upload GC** 与**离线对象核对**两条任务线，五条导出线连同容量调度草案（会再添两条）整体延后；下表第三列的"亲和/worker"相关约束届时才生效。

| 形态 | 适用 | 约束 |
|---|---|---|
| **单实例** | 最小部署 | 后台任务与 API 同进程。无任何额外要求 |
| **API 多实例 + 任务单实例** | 需要水平扩展读/写时 | 任务进程独立部署，靠配置开关关闭 API 侧的任务注册。**注意**：此形态下导出**亲和失效**（"接收请求的机器"没有 worker），退化为全局 claim——不是错误，只是没生效（08-导出 §7.1） |
| **API + worker 全多实例**（推荐） | 水平扩展与导出压力同时存在 | 每个实例同时承载 API 与 worker ⇒ **亲和生效**。七个任务全部可直接多实例跑；导出 worker 靠**亲和锁**（08-导出 §7.1），其余靠各自的 CAS / 唯一键仲裁 / 谓词幂等 |

**导出亲和的前提是"每个实例都跑 worker"**：亲和把任务绑给"接收请求的机器"，若那台机器没有 worker 去消费，锁会空占 `lease` 后自然过期。**API 与 worker 分离部署时不要期待亲和带来收益**——它在功能上无害（退化为旧行为），但白拿不到"同机处理"的好处。

**"回收者不能是被回收者自身"这条与部署形态无关**：租约恢复必须是独立任务，否则 worker 池整体崩掉时无人收尸（09-回收与后台任务 §6）。

### 3.2 上线步骤

```
1. 建表（8 张，DDL 见 .prd/SQL设计.md）
2. 写入 store 初始行（含真实 SK）—— 该 SQL 不进 git，由运维部署后单独执行一次
3. **厂商桶配置 CORS**（仅浏览器直传场景需要；见 §3.4。不做则分片整片失败，而代码里看不出来）
4. 启动自检通过（§1）—— 任一项失败即拒绝启动
5. 先只读放量（公网 URL 解析走新代码），再开放写
6. 逐项打开后台任务（首版仅两条：upload GC → 离线对象核对；五条导出线随导出功能延后）
```

### 3.3 监控与告警

| 指标 | 用途 |
|---|---|
| 上传成功率 / 各失败原因分布 | 区分"参数错"与"系统错" |
| **秒传命中率** | 内容寻址的核心收益指标；下降说明摘要口径或缓存出问题 |
| 分片会话数 / GC 回收数 | 会话泄漏的早期信号 |
| **导出队列深度**（`status IN (0,3)` 计数） | 队列深度持续上涨 = worker 不够或任务卡住 |
| 导出失败率 / 终态失败数（`status=3 AND retry>=maxRetry`） | 需要人工介入的信号 |
| **零引用 `object` 行数** | 离线核对的产出；持续增长说明回收路径有系统性缺陷 |
| `app_config` 缓存命中率 | 延迟双删是否正常工作 |

**必须告警**：启动自检失败（服务起不来）；离线核对发现的孤儿数**持续增长**（不是绝对数——存量孤儿是已知接受项，增长才是问题）。

### 3.4 运维脚本（不在服务内）

| 脚本 | 用途 | 注意 |
|---|---|---|
| store 初始数据 | 写入含真实 SK 的行 | **不进 git** |
| 目录策略回溯 | 把某批目录冻结到当前 `app_config.default_*` | 快照式**没有"是否被人工覆写过"的信息**，只能全量覆写，会冲掉人工设定（04-directory §8） |
| 桶侧对账 | 枚举桶 × `object` 表双向比对 | 唯一能发现 **B 类残留**（行已删、桶对象还在）的手段；本设计不提供常驻实现 |
| **厂商桶 CORS** | 放行客户端来源，使**预签名分片 URL 可跨域 PUT** | **直传的前提**（06-upload §6.2，含 `chunkCount=1` 单片）。不做则整片失败，而这是**桶侧配置、代码里看不出来** ⇒ 必须进交付清单；只在浏览器直传场景需要 |
| **厂商桶"服务端加密"开关** | 必须**关闭**（或确认分片 ETag 仍等于内容 MD5） | 开了 SSE 会让 ETag 变成密文摘要 ⇒ 摘要核验**误拒所有分片上传**（12-工程与交付 §1 第 7 项、06-upload §4.2） |

## 4. 实现顺序

按"依赖被依赖者先落地"排序，每步都可独立验证。

| 阶段 | 内容 | 验收 |
|---|---|---|
| **S1 地基** | `entity.BaseModel`、8 个 entity、`pkg/{objectkey,provider,chunk,pattern}` | §2.1 单测全绿 |
| **S2 配置面** | `store` / `app_config` 的 entity + repository + dbs + service；`infra/store` registry 与 Client | §1 自检项 1/2/3/5/6 可跑；`GetClient` 可用 |
| **S3 目录** | `directory` 全套；`EnsurePath`；移动与删除 | 删/移子树的 SQL 与转义单测；限深与防环用例 |
| **S4 上传主链路** | `object` + `upload` + `file`；预上传、直传（含 `chunkCount=1` 单片）、完成事务、幂等四收口 | §2.2 并发用例；`size` 两层校验用例；**会话召回/续传用例**（重进后只补缺口、同键并发只一行会话、`NoSuchUpload` 弃用重建） |
| **S5 导出** | `export_task` + `export`；摘要口径；worker 池（含心跳）；租约恢复；三条清理线 | 状态机全跃迁用例；CAS 竞态用例；心跳停摆与 `failed_at` 刷新用例 |
| **S6 回收与核对** | `A − B` 回收；离线对象核对；重试队列 | 孤儿/悬空行的方向性用例 |
| **S7 接口与运维** | proto 全套 + app 层 handler + 错误码；监控指标；运维脚本 | §2.3 契约测试；§2.4 自检负例 |

**S1–S3 与 S4–S5 可以并行**，只要 `pkg/` 与 `entity` 先冻结。
**⏸ 首版实现顺序（2026-10-13 定，README §1.1）**：导出功能整体首版不实现 ⇒ **S5 整体推迟**（但 `export_task` / `export` 两张表的 DDL 与 entity 随 S1 一起建/写，供启动自检覆盖），S6 只做 `A − B` 回收与离线对象核对；S7 的 `ExportService` handler 推迟。S2–S4 是首版主路径。
