## 1. 表语义

一行 = 一次进行中的分片上传，是厂商侧 multipart upload 的镜像。**表里只有活跃会话**：合并成功或中止即删行，"行存在 = 会话活着"，没有状态列。

```go
// repository/upload.go
type Upload interface {
	// GetUpload 命中会话；必须带 user_id 做鉴权，查不到即"会话不存在"
	GetUpload(ctx core.Context, uploadID string, userID uint64) (*entity.Upload, error)
	// CreateUpload 建会话；撞 uidx_upload_session 即触发召回（调用方重查、验活、复用既有行，见 §6/§7）
	CreateUpload(ctx core.Context, ent *entity.Upload) (uint64, error)
	// TouchUpload 顶 updated_at（滑动过期时钟，传片时调用）
	TouchUpload(ctx core.Context, id uint64) error
	// DeleteUpload 删会话（完成事务内 / Abort 后）
	DeleteUpload(ctx core.Context, id uint64) error
	// ListExpiredUpload 扫过期会话（GC 用）
	ListExpiredUpload(ctx core.Context, before int64, limit int) ([]*entity.Upload, error)
}
```

**会话的三个事实 + 三个放置事实**：`store_keyword` / `md5` / `ext` 是会话创建时确定的三个事实（GC 现场重建调用上下文所需的全部信息——没有它们 GC 无法构造 `AbortMultipartUpload`）；`user_id` / `directory_id` / `name` 是三个**放置事实**，消费点都在完成事务（file 行诞生时必须知道它们，而 GC 补合没有请求上下文、客户端重传 Complete 也不携带服务端解析出的 `directory_id`，所以必须随会话落库）。

**会话的身份 = `(store_keyword, md5, user_id, directory_id)`（唯一键 `uidx_upload_session`，2026-10-13 定）**：同一用户对同一目录、同一内容，全局只有一个在飞会话；同键并发 Prepare 由唯一键仲裁，撞键方重查复用赢家，没有"选哪个会话"的问题。秒传判定只查 `object`、与在飞会话无关——字节已在桶里时直接秒传，在飞会话留给 GC（§6 步骤 6 的顺序不能反：先秒传、后召回、再新建）。

## 2. 会话鉴权只有一处

```go
// 查不到即拒绝，且一律返回"会话不存在"——不区分"不存在"与"不是你的"，
// 否则 uploadId 的有效性就成了一个可探测的 oracle
ent, err := repo.GetUpload(ctx, uploadID, userID)
```

**它守着两个入口**（2026-10-13 补）：**取分片上传地址**（§6.2，拿到地址就能往别人的会话里写字节）与**完成**（§7.2）。传片本身不再经过服务端（§5 全部直传），所以"传片"这一步没有校验点——**这正是取地址必须鉴权的原因**。

**为什么必须做**：会话行持有的是**创建者的** `user_id` / `directory_id` / `name`，而完成只需要 `upload_id`。若只凭 uploadId 放行，任何拿到它的人都能操作别人的会话。注意 **§4.2 的摘要核验落地之后，这条路已经产不出"内容替换"**——攻击者传的字节算出来的摘要必然对不上会话声明的值，§7.1 判据 4 会拦下。剩下的危害是**拒绝服务**：污染分片让真正的上传者永远合不上，或直接 `Abort` 掉别人的会话。加一次 user 比对把这两件事一起关掉，代价只是一次索引比对。

> 这是摘要核验的**连带收益**：鉴权从"防止内容被替换"降级为"防止会话被干扰"，而前者危害远大于后者。但**不能因此省掉 user 比对**——DoS 同样是事故，而且它还兜着 `directory_id` / `name` 的归属正确性。

**不叠 app 校验**：manager 侧 `user.id` 全局唯一，user 比对已隐含租户隔离。因此 `upload` 表不需要 `app` 列——`app` 回答"哪个租户"，`user_id` 回答"谁"，这里要回答的是"谁"。

## 3. 两样刻意不存的东西

**没有 `chunkSize` / `chunkCount` 列**：切片粒度是**代码里的推导函数**（§4.1），由服务端下发给客户端——**权威下发点是专门的取片大小接口（§6.1），预上传响应里仍带一份（客户端实际切片必须与它逐位一致），但客户端算 `md5` 只能用先取到的那个值**。原因是客户端必须**先拿到它、才能按片算出 `md5`、再带着 `md5` 去调预上传**（§4.2）。它是传输参数，不是会话属性、不是文件属性、不是 app 属性；`chunkCount = ceilDiv(total_size, chunkSize)` 在同一会话内是精确的派生值，合并时服务端自算。

**没有已传分片进度 / 片级 ETag**：分片接收的权威记录在厂商侧 `ListParts`。自建计数器要落在"厂商调用成功、我们写库失败"这个不确定边界上，一漂就两种坏结果：漂少了，物理完整的对象永远合不上，而客户端**无法补回这条记录**（它每片都发成功了），只能整份重传；漂多了，缺片的对象被合出来。

## 4. 服务端推导的两样：`chunkSize` 与 `md5`

两样都是**由服务端决定、客户端必须照做**的量，且第二样依赖第一样（摘要按切片算），所以放在同一节。

### 4.1 `chunkSize`（整数、MB 对齐）

```go
const MB = 1 << 20

// Size 推导分片大小：max(5MB, ceilDiv(totalSize, 10000*MB) * MB)，全整数运算、5MB 下限（MB 对齐保留）
// 超过物理天花板时返回 error，不得静默截断
func Size(totalSize uint64) (uint32, error)

// Count 推导片数：ceilDiv(totalSize, chunkSize)
func Count(totalSize uint64, chunkSize uint32) uint32

func ceilDiv(a, b uint64) uint64 { return (a + b - 1) / b }
```

等价说法：**不小于 `totalSize / 10000` 的最小 1MB 整数倍**，且不低于 5MB（下限已从 1MB 抬到 5MB）。四条性质各有用处：

1. **结果永远是 1MB 的整数倍**（5MB 下限本身也是 1MB 的整数倍）——客户端切片不会出现"半个字节"的边界歧义，合并判据的"除末片外每片 `Size == chunkSize`"也就有了干净的比较基准。
2. **片数必然 ≤ 10000**：`chunkSize ≥ totalSize / 10000` ⇒ `chunkCount = ceilDiv(totalSize, chunkSize) ≤ 10000`。这是把厂商"单个 multipart 最多 10000 片"的硬上限**吸收进公式**，而不是事后再判。注意 `totalSize / 10000` 那一步**也必须是向上取整**：用整数除法向下取整，会在 `totalSize` 恰好跨过 10000 分界时算出 10001 片。
3. **50GB 以内 `chunkSize` 恒为 5MB**（`totalSize ≤ 10000 × 5MB` 时 `ceilDiv(totalSize, 10000×1MB)` 的结果乘 1MB 后仍 ≤ 5MB，被 5MB 下限兜成 5MB），与"固定 5MB"完全等价。
4. **全程整数运算，禁止 `math.Ceil(float64(...))`**。理由不是浮点会失真（`totalSize` 上限远在 `2^53` 之内），而是**这个值必须与任何一处重算逐位一致**——服务端下发它、GC 补合时服务端还要自算 `chunkCount`、客户端也可能拿它反推。整数运算的一致性可证明，浮点只是"看起来一致"。

**`totalSize = 0` 直接拒绝**（EMPTY_FILE）：空文件 `chunkCount = ceilDiv(0, chunkSize) = 0` 是退化值——没有片、无法建会话、无法切片，下游全部错位。`Size()` / `Count()` 入口校验 `totalSize ≥ 1`，为 0 立即返回 EMPTY_FILE，**不进入后续流程**（含秒传查询）；`GetUploadChunkSize`、`PrepareUploadFile` 在 API 边界同样拒绝（10-接口契约）。空对象（大小为 0 的占位）本设计不支持，若要放开需单独评估对象键与 ETag 语义。

**全局 5MB 下限**（2026-10-13 拍板"按照5M处理"）：不再按厂商分下限。AWS S3 要求除末片外 ≥5MB（1MB 会被 Complete 直接拒掉），BOS / OSS 允许百 KB 级但也接受 5MB，所以把公式下限直接抬到 5MB 就能对**全体目标厂商合法**——公式与 provider 解耦，无需在接入新厂商时复核下限，`GetUploadChunkSize` 也因此不必带 provider 入参（简化）。末片允许小于 5MB，符合各厂商规则。

**上界**：`chunkSize` 超过 `uint32` 需要 `totalSize ≈ 42.94 TB`（推导见 10-接口契约）。因此 proto 的 `chunkSize` 保持 `uint32`，**代价是单文件上限被隐式钉在该值**——计算处加断言，超界即报"文件过大"，**不得静默截断**（截断会让服务端下发的值与客户端实际切片不一致，表现为永远合不上）。**不另造业务常量**：上界由公式与类型推导得出，人为取一个更小的值只会多一个需要同步的地方。

### 4.2 `md5` —— 分片摘要的摘要（2026-10-13 定）

**规则**：按 §4.1 的 `chunkSize` 把内容切成 N 片，逐片取 MD5 得到 N 个 32 位小写 hex，**按片号升序拼成一个长 hex 串**，再对这个串取一次 MD5：

```
md5 = MD5( hex(md5(part₁)) ‖ hex(md5(part₂)) ‖ … ‖ hex(md5(partₙ)) )
```

拼接的是 **hex 文本**，不是二进制摘要——**不要**照抄厂商多段对象的 ETag 规则（那是"二进制摘要拼接 + `-N` 后缀"），两者不是一回事。

**为什么不是"整文件 md5"**：服务端必须能**独立重算**它，否则"客户端声明的摘要与服务端算的一致"就只是一句空话。而直传路径下服务端**拿不到任何分片的字节原文**（§5 已定：上传**客户端直传厂商**，服务端只有厂商 `ListParts` 返回的分片 ETag），能独立算出的摘要就是"分片摘要的摘要"。整文件 md5 要成立，就得把所有字节拉回服务端——那等于放弃直传、把带宽代价加回自己身上。

**单片路径必须用同一条规则**：`total_size ≤ chunkSize` 时 N = 1，即 `md5 = MD5(hex(md5(整个文件)))`——**对文件 md5 再取一次 md5**，不是直接取文件 md5。否则同一份内容走单片与走分片会得到两个身份，去重与秒传同时失效。

**算与核的分工**：客户端**上传之前**算（它要拿它去查秒传，见 §6 第 6 步）；服务端在**对象诞生之前**独立重算并比对（§7.1 判据 4、§5.1）。核验不过 ⇒ **中止、不留对象**，不是"记一条不一致继续"。

**核验成本≈0**：所有上传都走 `ListParts`（合并判据本来就要调，必查），它的每个 part 带 ETag，聚合即可——N 次 32 字节哈希 + 1 次 N×32 字节哈希，**不额外拉一次字节**。单片（`chunkCount=1`）也是同一套，只是 N=1。

**核验的厂商前提（2026-10-13 定：能力位 + 启动自检）**：直传路径（含 `chunkCount=1` 的单片）的核验建立在"`ListParts` 的分片 ETag == 该分片内容的 MD5"之上——这是**全部走厂商直传**（§5）的代价（经服务端中转就没有这个前提）。该前提在**未开启服务端加密**时成立，开启 SSE 后 ETag 变成密文摘要、核验会**误拒所有上传（含 `chunkCount=1` 的单片）**。处置：给 `pkg/provider` 行为表加一个"分片 ETag 是否等于内容 MD5"的**能力位**，并在**启动自检**里断言（12-工程与交付 §1 第 7 项）——**让它在启动时就炸，而不是在用户上传时静默误拒**。**不选"不一致只告警不拒绝"**：那等于核验不存在。

**这个规则把 `chunkSize` 抬成协议契约**：`chunkSize` 一变 ⇒ 切片边界变 ⇒ **每一份已有内容的 `md5` 都变** ⇒ 对象键 `{md5}.{ext}` 全变。所以公式的冻结级别与"对象名格式"同级（01-基础设施 §5），**不能当普通常量调**。时机上现在是清库重建、无历史数据，**改规则的成本此刻为零**；一旦上线，对象键就是对外承诺。

**顺带收益**：按片核验能**定位到是哪一片坏了**，比整文件 md5 的"整体不一致"强——而"防链路截断"正是这一列原本宣称的作用（05-object §6.1）。

### 4.3 前端实现约束（浏览器，2026-10-13 拍板保留）

保留"上传前秒传"⇒ 前端**必须**在上传前算出 §4.2 的摘要（逐片读字节取 MD5 再聚合）。这带来两个浏览器侧硬约束：

- **浏览器没有原生 MD5**：`crypto.subtle.digest` 只支持 SHA 族、不含 MD5 ⇒ 前端必须用纯 JS 库（如 spark-md5）或 WASM 实现（hash-wasm，比纯 JS 快 2–5 倍），**不可假设平台提供 MD5**。
- **必须在 Web Worker 里算**：纯 JS 对大文件哈希很慢——手机单线程 JS 吞吐约 30–70 MB/s，2GB 文件约 **30–60s**（弱机 / 降频可达 90s），台式机 native 仅几秒但前端用不上。放主线程会冻结 UI；放 Worker 后 UI 不卡，但"点上传后开始传"仍被挡在全量哈希之后（秒传要求先拿到聚合键才能查重）。
- **每片 MD5 复用为 `Content-MD5`**：随每个 `UploadPart` 发给厂商，让**厂商自己**在收片时拒绝传输损坏的 part——与 §4.2 的摘要核验是两条独立防线（前者挡链路损坏、后者挡声明与事实不符），一算两用。
- **读字节不重复**：切片本就要把每片读出来上传，哈希复用同一份读取，边际成本只是哈希 CPU，不额外读盘。

> 若将来接受"完成后去重"（放弃上传前跳过），前端可完全不算 MD5，仅可选 `Content-MD5`；但该路径**只能配聚合键**（服务端从 `ListParts` ETag 派生键后查重），文件 MD5 键因服务端无字节永远做不到。本次保留上传前秒传，故上述约束生效。

## 5. 上传总览

**三条通道的共同前置**（2026-10-13 定）：客户端先调 §6.1 取片大小 → 按 §4.2 算出 `md5` → 再进入下表。**秒传也逃不掉这一步**，因为 `md5` 的算法依赖切片边界，而切片边界由服务端定。

**客户端不传 store**——落桶完全由 `app_config.store_keyword` 决定。让调用方指定落哪个桶是越权，既能把 A 的数据写进 B 的桶，也能绕过 `app_config` 直接挑走导出桶。

| 路径 | 触发条件 | 字节流向 | 是否建会话 | `file.upload_id` |
|---|---|---|---|---|
| 秒传 | 预上传命中 `object` 且 `size` 相符 | 不写字节 | 否 | NULL |
| 多段直传（含 `chunkCount=1` 的单片） | 预上传未命中（全部走厂商 multipart） | **客户端 → 厂商**（直传，预签名 URL） | 是 | 厂商 uploadId |
| GC 补合 | 会话过期但判据齐 | —（字节已在厂商侧） | 用既有会话 | 厂商 uploadId |

**字节流向：全部直传厂商**（2026-10-13 改）：

- **所有上传（含 `total_size ≤ chunkSize` 即 `chunkCount=1` 的单片）都走"客户端直传厂商"的 multipart 上传**：服务端只做控制面——建会话、`GetUploadPartURLs` 下发预签名分片 URL、查 `ListParts`、发 `Complete`；分片字节**从不经过服务端**。理由是带宽——即便是 ≤5MB 的小文件，经服务端中转也等于让本服务担一份出网流量与长连接。
- **不再有"单片经服务端"这条路径**：原设计里"单片经服务端、在 PUT 前哈希核验"的例外已撤销（见下方"反面选项反转"）。统一后，单片就是 `chunkCount=1` 的一段 multipart 上传，核验机制与分片**完全一致**——都在 `CompleteMultipartUpload` 之前用 `ListParts` 的分片 ETag 比对（§7.1 判据 4）。
- 两条老的"单片 / 分片"通道合并为一条：都建会话、都走 `GetUploadPartURLs`、都在 `Complete` 前核验。

> **反面选项反转（2026-10-13 改）**：原先否掉的"把单片也做成 1 片 multipart、统一走直传"现在成为**选定方案**——用户以"统一走厂商直传"为优先，接受其代价（≤5MB 上传多约三次控制面往返：`InitiateMultipartUpload` + 一次分片上传 + `ListParts` + `CompleteMultipartUpload`；且每行上传都会写一条 `upload` 会话，交给 GC）。

### 5.1 单片（`chunkCount=1`）的核验同样发生在 Complete 之前

`total_size ≤ chunkSize`（即 ≤5MB）走 multipart 的 `chunkCount=1`：客户端上传那唯一"一片"、服务端在 `CompleteMultipartUpload` 之前用 `ListParts` 拿到这一片的 ETag、按 §4.2（N=1）重算 `md5` 比对——与分片路径**完全相同的核验机制**（§7.1 判据 4）。

**不再有"经服务端 PUT、PUT 前哈希"这条路径**：它原先存在的唯一理由是"单片没有 `ListParts`、直传只能事后 `HeadObject` 核验、而事后覆盖已发生"。统一走 multipart 后，单片也有 `ListParts`，核验得以在 `Complete` 之前完成——覆盖攻击在"对象诞生前"就被拦下，与分片一致。代价是 §5 所列的多约三次控制面往返与一行 `upload` 会话（已接受）。

## 6. 预上传（秒传判定 + 落桶解析）

**调用顺序**（2026-10-13 定）：客户端**先**调 §6.1 取片大小拿到 `chunkSize`，**再**按 §4.2 算出 `md5`，**最后**带 `md5` 调本接口。这是循环依赖的解法——`md5` 依赖切片边界、切片边界依赖 `chunkSize`，而 `chunkSize` 由服务端定；**不能让客户端自己实现公式**（公式是协议契约，复制到前端必然漂移）。代价是多一次往返（一个纯计算、无 IO 的接口）。

```
1. app = 请求上下文所属 app
2. cfg = appConfig.GetAppConfig(app)
   缺行 → 报"应用未配置"，不懒创建、不回落服务级默认
3. cfg.status == 0 或 store.status == 0 → 拒绝（AND 关系）
4. 解析目录：按 path 逐级定位，不存在则按 04-directory §7 自动建
5. 校验 accept / max_size（只读 directory 一行，不回读 app_config）
6. obj = object.GetObjectByMd5(cfg.StoreKeyword, req.md5)   // req.md5 = §4.2 的摘要
   命中 且 obj.Size == req.size → 秒传：直接建 file 行返回 URL（零字节写入、无需核验）
   命中 但 size 不符            → 拒绝（碰撞护栏）
   未命中                       → 查在飞会话（召回）：
       SELECT ... FROM upload
        WHERE store_keyword = ? AND md5 = ? AND user_id = ? AND directory_id = ?
       命中 → ResumeMultipart(upload_id) + ListParts 验活（§7.4 全量分页）：
                正常                          → 复用：返回 upload_id + 已传片号列表
                                                    （不自动 Complete——合并发起权仍在客户端，§7.1）
                NoSuchUpload                  → 删会话行，落"未命中"分支
                session.total_size 与 req.size 不符 → 拒绝（碰撞护栏，同秒传层口径）
       未命中 / 删行后 → 建会话（不论 `total_size`，含 `chunkCount=1` 的单片），
                        走 multipart 直传厂商，并返回 `upload_id`
```

**召回的两个硬约束**（缺一条就是把凭证或归属交出去）：

1. **匹配键必须含 `user_id` 与 `directory_id`**：`upload` 行持有会话凭证（`upload_id` 本身就是"往这片写"的能力，§6.2）与放置事实（目录、name）。只按 `md5` 召回 = 把别人的上传地址、别人的目录归属交给调用方——同一 `md5` 但不同用户/不同目录是**不同的事件**，必须各建各的会话。
2. **`name` 不进键**：命中后 file 行用**首调者**的 `name`（放置事实归首调者，与 `ext` 归首写者同构，05-object §4 细则 4）。重调 Prepare 带不同 `name` 不换会话，也不拒绝——以会话为准。

并发同键 Prepare 由唯一键仲裁（SQL 设计 §5）：`INSERT` 撞 `uidx_upload_session` 的一方重查复用赢家，与 `object` / `file` 撞键同一形态，**不需要锁、不需要 upsert**。

- **`size` 两层校验的完整定义在 **05-object §6**；第 6 步的"命中但 size 不符 → 拒绝"就是**秒传层**那一条。**`upload_id` 是本次上传的临时 token / 凭证**：客户端凭它取分片地址（§6.2）、最终调完成接口（§7.2）——新建与召回两条路径都返回它，客户端不需要自己保存它（§7）。

**秒传路径不做摘要核验，也不需要**：它不写任何字节，"对象身份"由既有 `object` 行决定，不存在被本次请求污染的可能。**客户端声明的 `md5` 在这里只有一个用途——查秒传**；对象的身份最终由**核验通过后的值**决定（§7.2）。

### 6.1 取片大小接口（新增，2026-10-13 定）

```
GetUploadChunkSize(totalSize) → { chunkSize, chunkCount }
```

- **纯函数、无副作用、不查库、不建会话**：输入 `totalSize`，输出 §4.1 的推导结果。因此可任意重试、可按 `totalSize` 分档缓存。
- **唯一职责是解开 §4.2 的循环依赖**。它是 `chunkSize` 的**权威下发点**；`PrepareUploadFile` 响应里仍带 `chunkSize`（客户端实际切片必须与它逐位一致），但**客户端算 `md5` 只能用本接口先取到的那个值**。
- **为什么不让客户端自己算**：公式含 `ceilDiv` 与"片数 ≤ 10000"上界（§4.1），是**协议契约**不是工具函数；前端复制一份就产生第二实现，任一侧调整都会让 `md5` 静默错位，表现为"所有分片上传都核验失败"。
- **超界即报错**：`totalSize` 超过 42.94 TB 时返回"文件过大"（§4.1 上界），不截断。

**一条必须守住的不变量**：内容不能落到不由上传方控制的桶里 ⇒ 第 6 步的查询必须带 `store_keyword` 限定，**禁止**全表按 md5 找（见 05-object §7）。

**读路径以 `object` 为准，不以 `app_config` 为准**（见 05-object §8）。

### 6.2 分片上传地址下发（预签名 URL）

上传字节直传厂商（§5）⇒ 服务端必须把"往哪儿传"交给客户端。**单独开一个接口，不塞进 `PrepareUploadFile` 响应**：

```
GetUploadPartURLs(uploadId, partNumbers[]) → [{ partNumber, url }]
```

- **为什么不塞进 `PrepareUploadFile`**：那样要一次性返回 `chunkCount` 个 URL，而 `chunkCount` 上界是 **10000**（§4.1）⇒ 响应体可达数 MB，且绝大多数 URL 在客户端开始传之前就已经过期。**按批取**同时解决"响应体积"与"TTL 覆盖范围"两个问题。
- **批大小要有上界**（如 200），入参走 `validate` 校验；`partNumbers` 必须落在 `1..chunkCount` 内，越界即拒（与 §7.1 判据 1 同一口径）。
- **必须做会话鉴权**：与传片、完成同一处（§2）——`uploadId + user_id`，否则拿到 uploadId 的人就能取到别人的上传地址。
- **TTL 由服务配置 `upload.partUrlTtl` 控制**（11-配置 §1），语义是"**一个批次从下发到传完**"的窗口，**不是整份文件的上传时长**。取太短会在传一半时 403；取太长等于把写入窗口放大。
- **URL 形态**：厂商 `UploadPart` 的预签名地址（含 `uploadId` 与 `partNumber`）。客户端**不解析**、原样 PUT；服务端**也不返回厂商 endpoint / bucket**（客户端不需要知道）。
- **失败模式**：取 URL 是纯读操作，失败不改会话状态，客户端重试即可。
- **它本身就是能力凭证**：拿到 URL 就能传该片 ⇒ 只发给会话所有者（上面的 user 比对），TTL 也要短到不足以被转发滥用。
- **本接口同时是 `upload.updated_at` 的续期点（`TouchUpload`，2026-10-13 定）**：直传后传片字节不经过服务端，"每次传片顶 updated_at"已不成立；一次按份上传的取址往返有十余次（每批 ≤200 片），它就是天然的滑动心跳。与召回命中（§7）共同维持 GC 时钟，**只多一次 `idx_upload_updated` 上的 UPDATE、不额外查库**。

> ⚠️ **浏览器场景要求厂商桶配置 CORS**：预签名 URL 是**跨域 PUT**，桶侧不放行来源就会整片失败——而这是**运维动作**，代码里看不出来 ⇒ 写进交付清单（12-工程与交付）。

## 7. 分片上传

**字节全程不经过服务端**（§5）：客户端拿 §6.2 的预签名 URL 直接把每一片 `PUT` 给厂商，服务端只做控制面（建会话、发地址、查 `ListParts`、发 `Complete`）。

**对象元数据在建会话那一刻写死**（2026-10-13 定）：`Content-Type` 由 `ext` 派生（见 `SQL设计.md` 第 4 节字段 `ext`），它必须在 **`InitiateMultipartUpload`**（= 服务端的 `NewMultipart`，§6 第 6 步建会话时）一并写入——**`UploadPart` 不接受元数据，`CompleteMultipartUpload` 也改不了它**。三条推论：

1. **这是直传的额外好处**：元数据由服务端写，客户端的分片请求里塞不进也改不动（厂商忽略分片请求上的 `x-amz-meta-*`）⇒ **客户端伪造不了元数据**。
2. **`ext` 必须在建会话时就是终值**——它本来就是会话的三个事实之一（§1），所以**没有新增约束**；但"`Content-Type` 从 `ext` 派生"这条因此有了明确的时间点：**`NewMultipart` 调用处**。
3. **不要规划任何"先传完再补元数据"的步骤**：那需要厂商侧 `CopyObject` 自拷贝（有成本、有失败面）。当前设计**不需要**——秒传复用既有对象、其余上传（含 `chunkCount=1` 单片）在 `InitiateMultipartUpload` 写元数据，三条路径都不需要事后改。

**不需要 `object.status`**，因为 `object` 行只在 `CompleteMultipartUpload` 成功后才插入，进行中的状态全部由 `upload` 承载：

| 阶段 | 谁执行 | 厂商侧 | `object` 行 | 状态在哪 |
|---|---|---|---|---|
| InitiateMultipartUpload | **服务端** | 分配 uploadId，无对象 | 无行 | `upload` 行存在 = 会话活着 |
| UploadPart × N | **客户端直传**（§6.2 预签名） | 分片暂存 | 无行 | 厂商侧（`ListParts` 是权威，库里不记进度） |
| CompleteMultipartUpload | **服务端**（先核验，§7.2） | 对象此刻才存在 | **此刻 INSERT** | 结束，此后"有行 = 可读" |
| Abort / GC 超时 | **服务端** | 分片释放 | 从未有过行 | `upload` 行删除 |

**断点续传 = 重调 `PrepareUploadFile`（召回式，2026-10-13 定）**：客户端刷新 / 重进 / 换设备后，带着**相同的 `md5` 与目录**再调一次预上传——秒传未命中则按 `(store_keyword, md5, user_id, directory_id)` 命中在飞会话，返回既有 `upload_id` 与已传片号，`GetUploadPartURLs` 只补缺口。**客户端不需要保存 `upload_id`**——它是召回的结果，不是续传的入参；`uidx_upload_session` 保证同键只有一个在飞会话，并发（两个标签页、重试）被唯一键收敛为同一个会话，分片内容与边界逐位相同 ⇒ 重复写同一片是幂等覆盖，"到齐"仍有定义。已持有 `upload_id` 的客户端也可直接走 §2 的 `GetUpload` 命中继续；未命中即会话已结束，重新 Prepare 会秒传命中（零字节）或召回新会话。**召回是只读的**：只 `ListParts`，不写厂商侧任何状态，合并仍由客户端显式 `CompleteUpload` 发起（§7.1）。

**召回顺带收窄两件事**：① 崩在 90% 的会话不再必然走到 GC `Abort`——同键重调 Prepare 即采用，省掉剩余流量与桶侧计费碎片；② `uidx_upload_session` 让"同用户、同目录、同内容"只有一个会话 ⇒ `ext` 由首调者固定，**⑰（同内容不同后缀并发上传的孤儿键）在这一维度上不可能发生**——不存在第二个会话去写第二个键；仅跨用户 / 跨目录仍留原状（README §3 第 12 条）。

### 7.1 合并判定

发起权在客户端，判定权在服务端。服务端无法区分"还有片在路上"和"客户端已经死了"，任何自发合并都会把没传完误判成传完。

| 时机 | 谁发起 | 行为 |
|---|---|---|
| 正常 | 客户端显式调 `CompleteUpload(upload_id)` | 服务端跑判据，齐则走**完成事务**；不齐返回缺失片号，**会话保持存活**，客户端补齐再调 |
| 兜底 | GC 扫到 `updated_at` 过期的会话 | **先跑同一套判据试合并**（客户端只是崩在最后一步、字节其实都到了，捡回来省一整份重传流量）；判据齐走同一套完成事务，不齐才 Abort |
| 否决 | 任何时机 | 判据任一不满足，永不合并，没有"尽力而为"分支 |

**判据**（`ListParts` 必须全量分页，每个 part 只有 PartNumber/Size/ETag）：

1. 片号集合恰好 `== {1..ceil(total_size / chunkSize)}`——缺号 = 没传完；号越界 = 客户端越界。只比数量不比编号不够。
2. 除末片外每片 `Size == chunkSize`，末片 `0 < Size ≤ chunkSize`——**末片允许顶满**（整倍数大小的文件，末片就是满片；写成 `<` 会把这类文件判成永远合不上）。这保证分片形状与下发的 `chunkSize` 一致，拦住客户端乱切。
3. `Σ Size == total_size`。
4. **摘要核验通过**：服务端按 §4.2 重算 `md5` 并与会话声明的值比对。输入是本次 `ListParts` 的**分片 ETag 序列**（按片号升序、逐片剥掉引号取 32 位 hex）；`chunkCount=1` 的单片即那唯一一片的 ETag。不符 ⇒ **不合并、`AbortMultipartUpload`、报错**（绝不能"先合了再删"，理由见 §7.2）。**注意取的是各分片 ETag 的聚合，不是 `CompleteMultipartUpload` 之后厂商返回的最终对象 ETag**——S3 系 multipart 的最终对象 ETag 为 `MD5(各片二进制 MD5 拼接)-N`，既不等于整文件 MD5、也不等于本设计聚合值，拿它比对必然失败。

> 判据 1~3 只证明"片都到齐了、形状对"，**证不了"内容就是客户端声称的那一份"**。判据 4 是唯一把"客户端声明"与"服务端事实"对上的那一条；缺了它，会话里的 `md5` 就只是一个未经验证的声明——这正是旧设计"服务端从不校验 `md5`"留下的缺口。

不用"最后一片请求带 `isLast` 标记"来省掉第三个接口：标记放错时机被拒后，客户端没有第二条带标记的请求可发，重试等于重传一片字节；显式 Complete 是纯控制调用，重试免费。

### 7.2 完成事务（T1）

**核验必须在 `CompleteMultipartUpload` 之前**，三步顺序固定：

1. `ListParts`（全量分页）→ 跑 §7.1 四条判据（**含摘要核验**）；
2. 判据齐 ⇒ `CompleteMultipartUpload`（对象**此刻才诞生**）；
3. 对象已存在 ⇒ 跑下面的完成事务。

**为什么不能"先 Complete 再核验"**：Complete 一旦成功，就以**客户端声明的 `md5`** 为键往桶里写了一份字节。若该键**已经被一份合法内容占用**（这正是投毒场景：声明别人的 `md5`、上传自己的字节），这次 Complete 就是一次**覆盖**——合法对象被替换，而 `object` 行还在，引用它的所有 `file` 立刻指向攻击者的内容。**核验前置让"摘要不符"的结局里根本没有对象诞生**，只需 `Abort` 释放分片，桶里零残留。

客户端 `CompleteUpload` 与 GC 补合**走同一条路径**，一个 DB 事务：

```go
err := ctx.Transaction(func(txCtx core.Context) error {
	// 1) 确保 object 行：按 (store_keyword, md5) 查，未命中才 INSERT
	//    size 取会话的 total_size（服务端事实），ext 取会话值
	//    并发下撞 uidx_object_store_md5 的一方重查复用赢家；size 不符则拒绝（碰撞护栏）
	// 2) INSERT file：app 由 SELECT app FROM directory WHERE id=? 派生（同时校验目录仍在）
	//    directory_id / name / user_id 取会话，upload_id 取厂商 uploadId
	// 3) DELETE 会话行
	//    file 行的出生时刻 = 会话行的死亡时刻
})
```

**并发竞态**：两个请求同时传同一份字节到同一个桶，两次 Complete 写同一个键（`{md5}.{ext}`）→ 物理对象覆盖一次且字节相同，无害；两条 INSERT 一条成功、一条撞 `uidx_object_store_md5` → 撞的那方按"已存在"处理、复用赢家的 `object.id` 和赢家的 `ext`（**注意此时不要用请求自己的后缀重新拼一次 URL 返回给调用方，要用赢家的行**）。**不需要锁、不需要 upsert、不需要占位再回填。**

### 7.3 幂等不靠状态列，权威在厂商侧

`ListParts` / `Complete` / `Abort` 返回 `NoSuchUpload` **一律当"会话已在厂商侧结束"**处理（已完成或已中止），不许冒泡成错误。此后按现场四收口：

| 现场 | 动作 |
|---|---|
| 会话行还在，桶里那份字节在（`object` 行已在，或行缺但 `HeadObject` 命中） | 客户端在厂商侧已合、完成事务未落地 → **重放完成事务**（并发重放由 `uidx_file_upload_id` 仲裁，只有一个生效） |
| 会话行还在，`object` 行缺且桶内无对象 | 会话确实被中止 → 删会话行（厂商侧已无可 Abort 的东西） |
| 会话行已删，按 `upload_id` 命中 `file` 行 | 上次完成事务已成交 → 返回那一行的 URL（重复 Complete 的重试落在这里） |
| 会话行已删，`file` 也未命中 | 会话过期且无产出 → 返回"需重新发起"（内容若已在桶里，客户端重新预上传会秒传命中，零字节） |

> **任何时候不得仅凭 `object` 行存在就断定本次上传成功**——对象行可能是别的上传者早先建好的。

### 7.4 `ListParts` 分页是硬前置

厂商侧分页返回，必须循环 `IsTruncated` / `NextPartNumberMarker`，否则超过一页（通常 1000 片）时续传列表与完成提交都会被截断。

## 8. 会话过期与 GC

GC 的完整逻辑（先验尸后清理）在 **09-回收与后台任务**。会话过期时钟就是 `updated_at`（滑动），由 `TouchUpload` 顶动——**直传后它有两个调用点（2026-10-13 定）：`GetUploadPartURLs` 每批取址（§6.2）与会话召回命中（§7）**。两者都是客户端与服务端的一次往返，一次按份上传必有十余次 ⇒ 健康会话持续续期；写死 `expired_at` 会在传输中途把 5GB/40 分钟级别的健康会话 Abort 掉（这正是当初不建该列的原因，直传后由"取址 + 召回续期"维持）。

**`upload.updated_at` 是全服务唯一一个仍然承重的 `updated_at`**：它是计时列，不是审计列。之所以不另开专列（如 `touched_at`），是因为这张表**唯一的 UPDATE 就是 `TouchUpload`**——不存在"无关写顶掉计时起点"的风险，而另开一列等于复制一个永远与它相等的字段。这个豁免只对 `upload` 成立，不要推广：`export_task` 的 `updated_at` 曾承担同样的职责，2026-10-13 已拆成 `leased_at` / `failed_at` 两个专列。见 01-基础设施 §7.1。
