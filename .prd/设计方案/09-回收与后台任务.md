## 1. 单文件删除

删 `file` 行 → 若 `SELECT 1 FROM file WHERE object_id=? LIMIT 1` 无引用 → 删 `object` 行 → 删桶对象。

顺序与理由同 §3。

## 2. 删目录：`A − B` 集合差

| 集合 | 定义 | 取的时刻 | 处置 |
|---|---|---|---|
| `A` | 子树里的 `file` 行指向的 `object_id`，去重 | **删之前** | — |
| `A ∩ B` | 删完之后，`A` 里仍有 `file` 行指向的 | 删之后 | **保留**（`object` 行与桶对象都不动） |
| `A − B` | 删完之后，`A` 里已无任何行指向的 | 推导 | **可回收** |

**顺序不能反**：`DELETE` 一执行，子树原来指向过哪些 object 就无从得知了。

```sql
-- 1) 删之前收集候选 A（join directory，一条 SQL 代替逐行点查）
SELECT DISTINCT f.object_id FROM file f JOIN directory d ON f.directory_id = d.id
 WHERE d.app=? AND (d.id=? OR d.path LIKE :pattern ESCAPE '\\');
-- 2) 一条 join-delete 删掉整棵子树的行（不必先把 id 集合取出来）
DELETE f FROM file f JOIN directory d ON f.directory_id = d.id
 WHERE d.app=? AND (d.id=? OR d.path LIKE :pattern ESCAPE '\\');
-- 3) 删完一次查出"仍被引用"的那些 —— 返回的正是 A ∩ B
SELECT DISTINCT object_id FROM file WHERE object_id IN (:A);      -- :A 按 500 分批
-- 4) A − (A ∩ B) = 可回收，批量 DeleteObject
```

**第 1~3 步必须在同一个事务内（T4）**：跨事务时第 3 步看到的是**另一个快照**——`DELETE` 尚未提交就查不出"已消失"这个事实，于是所有候选都被判成"仍被引用"，**一个对象都回收不掉**（不是偶发，是稳定失效）。同一事务内第 3 步能看到自己刚做的 `DELETE`（"读己之写"在 RR 与 RC 下都成立），所以这套写法**不依赖隔离级别**。

## 3. 两个顺序与一次复查

**第 4 步的 `DeleteObject` 必须在事务提交之后**：厂商调用无法回滚，放进事务里会把一个"可以重试的 DB 失败"变成"DB 已回滚、桶对象已经删了"的不可恢复状态。

**顺序：先删 `object` 行，再删桶对象**。两种失败残留并不对称：

| 顺序 | 残留 | 后果 |
|---|---|---|
| **先删行**（本设计） | 无行有对象 | 桶里多一份无人引用的字节，浪费计费但**不会让任何 URL 变成 404** |
| 先删桶对象 | 有行无对象 | 秒传会命中这一行并发出一个死链，**用户看到 404** |

**删桶对象前要再查一次 `(store_keyword, md5)` 是否存在**：第 3 步与第 4 步之间，同一份内容完全可能被重新上传（走真实写入路径、PUT 覆盖同一个键、并 INSERT 出一行新的 `object`）。此时若把键删掉，就等于删了新行的字节——新行立刻变悬空。命中即**放弃这次删除**。

## 4. 并发下是保守的，这是故意的

两个事务并发删不同引用、而它们共享同一个 `object` 时，双方都会看到对方那一行还没消失 → **双方都判定"仍被引用"→ 双方都保留** → 结果是"`object` 行与桶对象都留着、但零引用"的**孤儿**。方向刻意选成"**宁可留孤儿，不可留悬空行**"（01-基础设施 §8.3）：孤儿只是浪费字节、可被离线核对发现；悬空行是文件直接 404，属于"数据看起来坏了"。彻底消除要加锁或串行化，与本设计不加锁的立场冲突，不值得。

## 5. 离线对象核对

回收的失败残留分两类，**能被发现的手段完全不同**：

| | 形态 | 成因 | 能否用 SQL 发现 |
|---|---|---|---|
| **A 类** | `object` 行**还在** + 桶对象还在，零 `file` 引用 | ① 删行失败；② 两个事务并发删共享同一 `object` 的不同引用，双方都保留 | **能**，一条反连接，`idx_file_object` 支撑 |
| **B 类** | `object` 行**已删**、桶对象还在 | 删行成功、`DeleteObject` 失败 | **不能**，库里无行可查；只能"枚举桶 × `object` 表"，**本设计不提供** |

> ⚠️ **不要把这两类混起来**。B 类无法靠"扫零引用 `object` 行"发现——那一类的行已经没了、扫不到。B 类是"先删行"这个正确顺序（§3）的**固有代价**，不能靠调换顺序消除。

本设计只兜 **A 类**，落地为一条周期性任务，纯 SQL、按批：

```sql
-- 1) 找零引用的 object 行（分批）
SELECT id, store_keyword, md5, ext FROM object o
 WHERE NOT EXISTS (SELECT 1 FROM file f WHERE f.object_id = o.id) LIMIT 500;
-- 2) 逐行先删行；CAS 再查一次，防"扫描之后、删除之前"被新 file 行引用
DELETE FROM object
 WHERE id = ? AND NOT EXISTS (SELECT 1 FROM file f WHERE f.object_id = ?);
-- 3) 再删桶对象（键已在第 1 步读出）
```

三条约束与 §3 逐条对应：

1. **顺序仍是"先删行、再删桶对象"**，不能反——反过来的话，第 2、3 步之间那条 `object` 行会被**秒传**命中并发出死链。
2. **第 2 步必须带 `NOT EXISTS` 再查一次（CAS）**，不能裸删。第 1 步到第 2 步之间同一份内容可能被重新上传并建出新 `file` 行；裸删就删掉了一条**有引用**的行，紧接着第 3 步会删掉别人正在用的字节。CAS 不命中即跳过。
3. **第 3 步失败要能重试**：键在第 1 步已读出、不依赖行存在，把 `(store_keyword, md5, ext)` 记进一张重试队列即可。这条把 B 类残留从"每次厂商调用抖动"收窄到"**进程在第 2、3 步之间崩溃**"。`DeleteObject` 幂等，重试安全。

**成本**：反连接由 `idx_file_object` 支撑，但 `object` 是亿级表 ⇒ 按主键区间**分批**推进，不做单条全量 SQL。

## 6. 后台任务

统一通过 `ctx.AfterStart` 注册生命周期，停止走 `ctx.BeforeStop`。

| 任务 | 周期 | 逻辑 | 多实例安全（靠什么） |
|---|---|---|---|
| **upload GC** | 分钟级 | **先验尸后清理**：过期会话先跑合并判据试合并（**含摘要核验**——按会话声明的 `md5` 重算 ETag 序列；齐 → 完成事务，捡回一整份流量）；不齐 → `AbortMultipartUpload` → 删行。**多数过期会话在走到 GC 前已被召回采用**（客户端重调 `PrepareUploadFile` 同键复用，06-upload §7），GC 实际处理"客户端彻底放弃"的那批 | ✅ **完成事务的 `INSERT file` 撞 `uidx_file_upload_id` 仲裁**（只有一个生效，另一方按 06-upload §7.3 第 1 行"重放完成事务"处理）；`AbortMultipartUpload` 幂等；`DELETE` 第二次 0 行无害 |
| ⏸ **export worker 池** | 常驻轮询 | `ListClaimable` → ~~抢亲和锁~~ → `Claim` → **生产期间按 `heartbeat` 顶 `leased_at` 并续锁 TTL** → `MarkSuccess` / `MarkFailed` | ✅ ~~任务亲和（08-导出 §7.1）~~；claim 的 CAS 仍是最终仲裁 |
| ⏸ **export 租约恢复** | 分钟级（`leaseReclaimInterval`） | `status=1 AND leased_at < :now - :lease` → `status=3, failed_at=:now` | ✅ **谓词自带排他**：置 `status=3` 即脱离条件 |
| ⏸ **export 产出物清理** | 分钟级（`cleanupInterval`） | **CAS `status=2→4` 认领** → 删桶对象 | ✅ **CAS 收敛单点**（08-导出 §12）：`RowsAffected==1` 才去删。只靠 `status=4` 挡不住**同一轮**的两个实例 |
| ⏸ **export 任务行回收** | 小时级（`taskReclaimInterval`） | `status IN (2,3,4)` 且无 `export` 引用 → `DELETE` | ✅ `DELETE … WHERE id=?` 第二次 0 行，无副作用 |
| ⏸ **export 请求行过期** | 小时级 | `created_at < now - retention` → `DELETE` | ✅ 谓词幂等（删过的不再匹配）；**这条是让前两条收敛的关键** |
| **离线对象核对** | 天级 | §5 的三步；失败记重试队列 | ✅ `DELETE … AND NOT EXISTS` 的 CAS（§5 约束 2）；重复 `DeleteObject` 幂等（只多一次厂商调用） |

> **⏸ 首版范围（2026-10-13 定）**：导出功能整体首版不实现（README §1.1），上表五条导出线全部推迟；首版只上线 **upload GC** 与**离线对象核对**两条。容量感知调度草案（`.prd/草案-导出本地目录与容量调度.md`）还会再给本表加两条（本地清理、注册表维护），同样随导出延后——届时“七条任务线”的计数按草案 §6 变更。

**租约恢复必须是一个独立任务，不能只靠 worker 池顺带做**：worker 池自己崩掉时（进程 OOM、被 kill），池里没有活着的 goroutine 去回收自己领走的行，那些行会永远停在 `status=1`。这正是租约机制存在的理由——**回收者不能是被回收者自身**。

**三个 `Interval` 各自服务一件事，不要合并**：`cleanupInterval`（产物过期）、`leaseReclaimInterval`（僵死接管）、`taskReclaimInterval`（行回收）的合理周期相差两个数量级（分钟 / 分钟 / 小时），合并成一个 `export.interval` 会迫使快的被慢的拖住。

### 6.1 三条导出清理线的闭环

```
产出物过期 → 删桶对象、status=4
任务行回收 ← 需要"无 export 引用"，而这要等请求行散尽
请求行到期（retention，默认 30 天）→ DELETE
```

缺第三条，前两条的产出会永久堆在库里——**任务行的"无引用"条件永远不成立**。三条合起来才构成闭环。

**"仍然带无 `export` 引用"这个条件不能省**：还有请求行指着任务时不删。请求行是用户的历史，而任务行是它唯一的状态来源；删早了，用户的列表会从"失败"变成"已删除"。

**`status=4` 作为"物理已删"的标记**：删桶对象这个动作本身需要去重（重复 DELETE 虽幂等但会产生无效调用与日志噪音）。**但这个标记只防"下一轮"**——同一轮里两个实例都扫到 `status=2` 时，两边都会去删。所以认领动作必须是一条 CAS（`UPDATE … SET status=4 WHERE id=? AND status=2`），`RowsAffected==1` 才去删桶对象；详见 08-导出 §12（那里还给出为什么"删错"是有代价的：`export/{md5}.zip` 是同规格共用的键）。

> **请求路径不再复活过期产物**（2026-10-13 定，08-导出 §5）：过期任务（`status=2 AND expired_at<=now` 或 `status=4`）只读返回，重跑只能走用户手动重试（CAS `IN (2,3,4)`，`expired_at=0` 一并复位）。因此清理线的 `status=2→4` **独占过期行的写**，与原"复活 vs 清理"的谓词冲突结构性消除——不需要 `AND status IN (2,4)` 之类补丁。残留的唯一交叠是手动重试与清理线撞同一行（窄窗、用户显式触发、后果是下次重试再跑一遍），已显式接受。

**任务行删除后请求行仍可查**（历史记录），只是指向一个已不存在的 task——**这是刻意的**：请求行是用户的历史，不该因为产物过期而消失。此时列表查询查不到 task，前端显示"已过期/已删除"。请求行自己到期后整行删除、从列表里消失，这是保留期的正常结果。

**`retention` 是服务配置、不是 app 配置**：它是一条**数据保留政策**（"我们留多久历史"），与 `export_ttl`（产物保留期，"这份产物多久后作废"，按 app 配）不是同一层级。唯一硬约束：**`retention` 应当 ≥ `export_ttl` 的最大值**，否则会出现"产物还在、请求行已经没了"的空窗。

### 6.2 多实例部署：不需要选主（2026-10-13 16:55 定）

**本设计支持多实例部署，七个后台任务没有一条需要分布式选主**——上表"多实例安全"列就是逐条的凭据：每一条都有**自带排他**的机制（CAS / 唯一键仲裁 / 谓词幂等 / 任务亲和）。原先"首版按单实例部署"的约束**已解除**（12-工程与交付 §3.1）。

**唯一需要显式协调的是导出 worker**，而它的解法不是选主而是**亲和**：任务归创建它的实例，实例消失则锁 TTL 到期、任务自然被别的实例接管（08-导出 §7.1）。**不需要"在线实例表"**——TTL 免费给出这个语义。

**"回收者不能是被回收者自身"这条依然成立**：租约恢复是**独立任务**，不是 worker 池的一部分。这条与多实例无关，是"worker 池整体崩掉时谁来收尸"的问题。

**三类"多实例下会重复做、但结果无害"的动作，显式接受**（只多一次厂商调用或一次扫描，不改数据）：`AbortMultipartUpload` 重放、`DeleteObject` 重放、CAS 未命中前的那次扫描。判据仍是**"这个机制坏掉时会怎样"**（01-基础设施 §8.2）：这些都只影响**成本**，不影响**正确性**。
