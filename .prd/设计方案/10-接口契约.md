# 10 · 接口契约（proto）

> **本册范围**：proto 文件组织、字段类型约束、服务清单、错误码。
> **依赖**：01-基础设施（类型分层原理、错误处理分层）。**规范依据**：`.claude/rules/proto-and-api.md`。

## 1. proto 文件组织

```
api/
├── store/proto/store.proto + store_service.proto
├── app_config/proto/app_config.proto + app_config_service.proto
├── directory/proto/directory.proto + directory_service.proto
├── file/proto/file.proto + file_service.proto
├── export/proto/export.proto + export_service.proto
└── errors/proto/errors.proto
```

规则：

1. 每个服务拆成 `xxx.proto`（消息）+ `xxx_service.proto`（服务）。
2. `xxx_service.proto` 必须 import 对应 `.proto` 与 `google/api/annotations.proto`。
3. HTTP 路由通过 `google.api.http` 注解定义。
4. `package` 用 `resource.api.<service>`；`go_package` 用 `resource/api/<service>;<alias>`。
5. 字段命名 snake_case（生成 Go 代码自动转 CamelCase）。
6. **RPC 请求/响应消息命名必须用 `<MethodName>Request` / `<MethodName>Response`**。
7. **所有 Request 必须用 `validate/validate.proto` 限制参数**：字符串至少非空，外部输入字段必须设置合理长度上限或枚举范围。**Response 不加 validate**（返回内容由服务端构造，边界控制应在业务代码里完成）。
8. **HTTP 路由不使用 `{path}` 路径参数**（如 `/v1/resource/directory/{id}` 一律禁止）：所有入参均经 Request 字段绑定——`GET`/`DELETE` 走 query，`POST`/`PUT` 走 body（`body: "*"`）。故每个"查单个/删除"都要有一条不与他人 `method+path` 冲突的独立路径（如 `/{id}` 改为 `/detail` + `id` 走 query）。

## 2. 类型约束

类型分层的原理（DB / Go / proto 三层不要求一致、按"上界是否已知"分流）在 **01-基础设施 §3.4**。本册只给逐字段结论：

| 字段 | proto | 理由 |
|---|---|---|
| ids（`id` / `directoryId` / `parentId` / `ids`） | `uint32` | API 契约上限 `2^32-1` = 42.9 亿行；DB 用 BIGINT 只是不让这个上限提前到来 |
| `total`（分页计数） | `uint32` | 同上 |
| `createdAt` / `updatedAt` / `expiredAt` | `uint32` | Unix 秒，上限 **2106-02-07 06:28:15 UTC**——写成显式事实，不靠"还很远" |
| `page` / `pageSize` / `chunkCount` / `index` / `width` / `height` | `uint32` | 数量级天然小 |
| `chunkSize`（分片大小，字节） | `uint32` | **有窄上界**：要让 `chunkSize` 超过 `uint32` 需 `total_size > 4095 × 1MB × 10000 ≈ 42.94 TB`，既低于厂商单对象上限（BOS 48.8 TB）、又远超任何实际需求 |
| **`size`（字节度量）** | **`string`** | **无上界**，见下 |

**只有 `size` 需要超过 32 位**：`object.size` / `upload.total_size` 是 `BIGINT UNSIGNED` 字节，理由就是"`INT UNSIGNED` 上限 4 GB，而这张表天生服务分片上传的大文件"。API 若停在 32 位字节，单文件上限就被压到 4 GB，与本表的意图直接冲突。

**为什么单位不能退回 KB**（那样 32 位能到 4 TB）：两层 `size` 校验是精确字节比对（05-object §6），KB 取整会让它退化成"两边取整规则必须逐字一致"⇒ 随机拒绝上传。**所以 API 的 `size` 是字节，这是被校验倒逼的。**

**为什么声明 `string` 而不是 `uint64`**：proto3 JSON 本来就会把 64 位整数渲染成字符串，两者在前端看到的完全一样；但显式 `string` **不依赖"序列化器恰好这么做"**——换 protojson / grpc-gateway / 任何网关都是 string，契约诚实，也把"这个字段可能超过 32 位"写在了类型上。前端用 `Number(s)` 转换（JS 安全整数上限 `2^53` ≈ 9 PB，远超任何单文件）。

### 2.1 已登记的时间戳转换点

Go 侧的 `int64` 时间戳转 proto 的 `uint32` 处，**必须登记**。新增时间戳字段时把转换点补进清单；任何一个字段**改变语义**（例如从"Unix 秒"改成毫秒）→ 上界随之变化，清单立即失效、必须重新评估；**清单之外出现新的 `uint32(时间戳)` 转换视为违规**。

已登记清单（当前共 7 处，来源全部是 `entity.BaseModel` 的 `CreatedAt` / `UpdatedAt`，即 GORM 自动填写的 **Unix 秒** `int64`，转换点集中在接口层的 `toX` / `toView`）：

| proto 字段 | Go 来源 | 转换点 | 语义 / 上界 |
|---|---|---|---|
| `file.FileItem.created_at` | `entity.File.CreatedAt` | `internal/app/file/file.go` `toFileItem` | Unix 秒，≤ 2106-02-07 06:28:15 UTC |
| `store.StoreView.created_at` / `updated_at` | `entity.Store.CreatedAt` / `UpdatedAt` | `internal/app/store/store.go` `toStoreView` | 同上 |
| `app_config.AppConfigView.created_at` / `updated_at` | `entity.AppConfig.CreatedAt` / `UpdatedAt` | `internal/app/app_config/app_config.go` `toView` | 同上 |
| `directory.DirectoryView.created_at` / `updated_at` | `entity.Directory.CreatedAt` / `UpdatedAt` | `internal/app/directory/directory.go` `toView` | 同上 |

> `export_task` 的 `leased_at` / `failed_at`、`upload.updated_at` 等计时列首版不进 proto（导出线延后、GC 在进程内按 `int64` 直接用），故不在本清单。新增任一时间戳 proto 字段时，先在 Go 侧确认其为 Unix 秒，再把上表补一行。

## 3. 服务清单

**`FileService`**

| RPC | 说明 |
|---|---|
| `GetUserFile` | 响应含完整 `url`、`size`（`string` 字节） |
| `ListUserFile` | 分页 `total` 为 `uint32` |
| **`GetUploadChunkSize`** | **新增（2026-10-13）**：入参 `totalSize`，出参 `chunkSize` / `chunkCount`。**客户端必须先调它**，再据此切片算 `md5`（算法 06-upload §4.2；**前端在浏览器里如何算见 §4.3**）。**`totalSize = 0`（空文件）直接拒绝**（EMPTY_FILE，06-upload §4.1） |
| `PrepareUploadFile` | **请求不含 store**；请求 `md5` 为**分片摘要的摘要**（算法 06-upload §4.2；前端实现约束 §4.3）；响应含 `chunkSize` / `chunkCount` / `md5` / `uploadId` / **`uploadChunks`（已传片号；会话召回命中时非空，客户端只补缺口）**。**断点续传 = 重调本接口**（06-upload §7：秒传未命中 → 按 `(store, md5, user_id, directory_id)` 召回在飞会话；客户端无需保存 `uploadId`，换设备/刷新同效）。**`totalSize = 0` 直接拒绝** |
| **`GetUploadPartURLs`** | **新增（2026-10-13）**：入参 `uploadId` + `partNumbers[]`，出参 `[{partNumber, url}]`。**上传字节直传厂商**的预签名地址，**按批取**（含 `chunkCount=1` 的单片，06-upload §6.2） |
| **`CompleteUpload`** | 客户端显式发起合并；服务端跑合并判据（含摘要核验，06-upload §7.1）后 `CompleteMultipartUpload`。**所有非秒传上传（含 `chunkCount=1` 的单片）都走它** |
| `UploadFileByURL` | 从 URL 抓取并上传（服务端取到字节后**也走 multipart 直传厂商**，不对外暴露本服务字节） |
| `GetFileBytes` | 服务端代理字节（stream） |
| `UpdateUserFile` | 只允许改 `name` / `directoryId` |
| `DeleteUserFile` | 触发对象回收（09-回收与后台任务） |

**`GetUploadChunkSize`（2026-10-13 定）**：解开"`md5` 依赖切片边界、切片边界依赖服务端"这个循环依赖的接口。

- **入参 `totalSize` 用 `string`**（字节，与 `size` 同规、同上界理由）；**出参 `chunkSize` / `chunkCount` 用 `uint32`**（§2 已有逐字段结论）。
- **纯函数**：无副作用、不查库、不建会话，输入决定输出，因此可重试、可按 `totalSize` 分档缓存。
- **`totalSize = 0` 直接拒绝**：空文件 `chunkCount = ceilDiv(0, chunkSize) = 0` 是退化值（没有片、无法建会话/切片），`Size()` 入口即返回 EMPTY_FILE 错误，**不进入后续流程**（含秒传查询）。
- **它是 `chunkSize` 的权威下发点**：`PrepareUploadFile` 响应里仍带一份（客户端实际切片必须与它逐位一致），但客户端**算 `md5` 只能用本接口先取到的值**——顺序反了就是拿一个自己猜的边界去算摘要，服务端核验必然失败。
- **为什么不让前端自己算**：公式含 `ceilDiv` 与"片数 ≤ 10000"上界，是**协议契约**（06-upload §4.1/§4.2）不是工具函数；复制到前端就产生第二实现。

**`GetUploadPartURLs`（2026-10-13 定）**：**上传字节直传厂商**（06-upload §5）的配套接口。

- **入参**：`uploadId`（`string`）+ `partNumbers`（`uint32` 数组，**批大小有上界**，如 200，走 `validate`）；**出参**：`[{ partNumber, url }]`。
- **为什么按批取、不塞进 `PrepareUploadFile` 响应**：`chunkCount` 上界 10000，一次性返回会得到数 MB 的响应，且绝大多数 URL 在开始上传前就过期。按批取同时收敛**响应体积**与 **TTL 覆盖范围**。
- **必须做会话鉴权**（`uploadId + user_id`，同 06-upload §2）：URL 本身就是能力凭证——**拿到就能传该片**。
- **TTL 走服务配置 `upload.partUrlTtl`**（11-配置 §1），语义是"一个批次从下发到传完"，**不是整份文件的上传时长**。
- **客户端不解析 URL**（原样 PUT）；响应里**不出现厂商 endpoint / bucket**。
- **浏览器场景要求厂商桶开 CORS**——预签名 URL 是跨域 PUT，属**运维动作**，写进交付清单（12-工程与交付）。

**`DirectoryService`**：`GetDirectory` / `ListDirectory` / `CreateDirectory` / `UpdateDirectory` / `DeleteDirectory`。`parentId` **由 `path` 派生回填**（保持接入方视角）；`CreateDirectory` / `UpdateDirectory` 不接收 `parent_id`；`UpdateDirectory` 承担改名与移动两种语义（移动走 04-directory §4）。

**`ExportService`**：创建导出（`md5` 按 08-导出 §3.1 口径；查询必须带 `app` 限定）/ 列表导出（固定两条 SQL；“下次重试时间”现算）/ 获取导出（`url`；下载时 `Content-Disposition` 用请求行 `name`）/ **手动重试**（对应 08-导出 §8 的 CAS UPDATE）。**⏸ 首版不实现**（2026-10-13 定，README §1.1 范围声明）：proto 可先生成，app 层 handler 与 service 推迟；两张表的 DDL 首版照建。

**`StoreService`**（管理面）：`ListStore` / `GetStore` / `CreateStore` / `UpdateStore` / **`ListProvider`**。**没有 Delete**。`sk` 只进不出——任何查询/列表接口只返回掩码，明文只在写入路径接受。

**`ListProvider`（2026-10-13 16:55 定）**：返回**代码里已注册的厂商清单**，供前端渲染下拉，响应元素为 `{ value, label, implemented }`。

| 字段 | 含义 |
|---|---|
| `value` | 写进 `store.provider` 的字面量：`aws` / `bos` / `oss` / `cos` / `obs` / `minio` / `uss` |
| `label` | 展示名（厂商中文名 / 产品名） |
| `implemented` | 该厂商的**行为表是否已实现**（寻址方式、域名族、分片下限、签名方式） |

- **为什么不放 `AppConfigService`、也不另开 service**：`provider` 是 `store` 的属性 ⇒ 归 `StoreService`（管理面）。新开一个 service 只为一次下拉不划算。
- **为什么不落库、不查 DB**：`provider` 白名单是**代码常量**（11-配置 §2 已列在"代码常量"层），它就是 `pkg/provider` 行为表的键集合。接口只是把这个集合**读出来**——落库会出现"表里有、代码不认"（或反之）的第二事实源，而这正是 11-配置 §2 把白名单放在代码常量层要避免的。
- **为什么必须有这个接口**：前端**不许硬编码**厂商列表。硬编码就会出现"前端有、后端拒绝"（启动自检第 2 条会拒）或"后端新增、前端看不到"。`implemented=false` 让前端**置灰**而不是让用户选完再被拒——把"未实现"变成可展示的事实，而不是一个运行时报错。
- **`implemented=false` 与启动自检的分工**：自检第 2 条（`provider` 在白名单内）**只认白名单**，不因 `implemented=false` 而放行写入——`implemented` 是给前端看的，不是给写入校验看的。写进一个行为表为空的 provider，仍然会被启动自检或运行时的行为表查询拒绝。

**`AppConfigService`**（管理面）：`ListAppConfig` / `GetAppConfig` / `CreateAppConfig` / `UpdateAppConfig`。**没有 Delete**（2026-10-13 16:33 定，与 `StoreService` 同立场）——下线一个 app 的配置 = `status=0`，走 `UpdateAppConfig`，从而自动带上延迟双删。理由与前提见 `03-app_config.md` §6.5 第 2 条。
