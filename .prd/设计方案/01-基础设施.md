## 1. 分层与依赖方向

```
app  ──►  domain/service  ──►  domain/repository (interface)
                                      ▲
                              infra (implements)
```

| 层 | 目录 | 职责 | 硬约束 |
|---|---|---|---|
| core | `internal/core/` | 配置单例、`core.Context` 扩展、App 初始化 | 全局唯一配置入口 |
| types | `internal/types/` | 请求 DTO | **不 import entity**，只有 JSON tag |
| domain/entity | `internal/domain/entity/` | 表对应的纯结构体 | **不依赖任何层**，只有字段 + 简单方法 |
| domain/repository | `internal/domain/repository/` | 仓储接口（含外部客户端接口） | 只依赖 core / entity / types |
| domain/service | `internal/domain/service/` | 业务编排 | **不 import infra**、不直接 import DB/Redis |
| infra/dbs | `internal/infra/dbs/` | 仓储实现 | 单例 `sync.Once`，方法名与接口逐字一致 |
| infra/store | `internal/infra/store/` | 厂商对象存储客户端 | 实现 `repository.Store` |
| app | `internal/app/` | handler + `init()` 自注册 | **唯一**做依赖注入的地方 |
| pkg | `internal/pkg/` | 无状态纯函数 | **不依赖任何 internal 业务包**，可被各层自由引用 |

### 1.1 `internal/pkg/` 承担的结构性角色

有几处知识**同时被 service 层与 infra 层需要**，放任何一边都会让另一边违反依赖方向。它们统一放 `pkg/`（中性包）：

| 包 | 内容 | 为什么不能放 domain 或 infra |
|---|---|---|
| `pkg/objectkey` | `ObjectName` / `ExportObjectName` / `ParseObjectName` | service 拼 URL、infra 拼对象键都要用 |
| `pkg/provider` | `(provider, region) → 行为` 表、`CanonicalEndpoint`、`AddressingStyle` | 写入校验（service）与建客户端（infra）都要用 |
| `pkg/chunk` | `chunkSize` 推导、`chunkCount` | service 下发、GC 补合时 service 自算 |
| `pkg/pattern` | `EscapeLike` / `PrefixPattern` | service 拼子树谓词、离线脚本共用同一实现 |

> 这是"domain 不 import infra"的直接推论：**跨层共用的知识必须下沉到中性包**，而不是靠"让 service 调一个 infra 接口"绕过依赖方向。

## 3. 数据模型映射

### 3.1 表 → entity

### 3.2 本项目必须自建 `BaseModel`

`kratosx/model.BaseModel` **不可用**（`kratosx@v1.2.9/model/model.go:12-16`）：

```go
type BaseModel struct {
	Id        uint32 `json:"id"        gorm:"primaryKey;autoIncrement;comment:主键ID"`
	CreatedAt int64  `json:"createdAt,omitempty" gorm:"index;comment:创建时间"`
	UpdatedAt int64  `json:"updatedAt,omitempty" gorm:"index;comment:修改时间"`
}
```

两个冲突：

1. **`Id uint32` vs DB 的 `BIGINT UNSIGNED`**。API 契约上限确实是 42.9 亿行，但 DB 用 BIGINT 的意图正是"不让这个上限提前到来"（SQL 设计文首"类型分层"），而 entity 层的职责是**与 DB 对齐**——用 `uint32` 会让 42.9 亿之后的行读出来是截断值，**且没有任何报错**。
2. **两个时间字段带 `gorm:"index"`**，会给每张表多建两个单列索引。本项目全部索引都在 DDL 里显式声明（`idx_upload_updated` / `idx_export_task_claim` 等），多出来的 `created_at` / `updated_at` 单列索引既无用，又要在每次写入时维护。

因此自建 `internal/domain/entity/base.go`：

```go
package entity

// BaseModel 本项目通用字段：Id 对齐 DB 的 BIGINT UNSIGNED，时间戳为 Unix 秒
type BaseModel struct {
	Id        uint64 `json:"id"        gorm:"primaryKey;autoIncrement"`
	CreatedAt int64  `json:"createdAt" gorm:"column:created_at"`
	UpdatedAt int64  `json:"updatedAt" gorm:"column:updated_at"`
}
```

- **不加 `gorm:"index"`**——索引全部由 DDL 负责。
- **不写 `omitempty`**——时间戳为 0 本身是异常信号，不该被 JSON 悄悄吃掉。
- **字段名保留 `CreatedAt` / `UpdatedAt`** 是有意的：GORM 按字段名识别整数自动时间戳（§7）。

### 3.3 字段注释（强制）

`.claude/rules/code-style.md` 要求每个字段行尾必须有中文注释，且：

| 字段特征 | 必须说明 |
|---|---|
| 枚举 / 有限取值 | 列出全部合法值 |
| 时间字段 | 说明单位：`Unix 秒` |
| 可空指针字段 | 说明 NULL 的语义 |
| 普通字段 | 简短用途 + 业务约束或取值范围 |

```go
// ExportTask 导出产出物
type ExportTask struct {
	App          string  `json:"app"          gorm:"column:app"`           // 应用标识
	Md5          string  `json:"md5"          gorm:"column:md5"`           // 产出规格摘要（非 zip 字节摘要）
	StoreKeyword string  `json:"storeKeyword" gorm:"column:store_keyword"` // 产出物实际落地的存储后端
	Size         uint64  `json:"size"         gorm:"column:size"`          // 产出物大小（字节）
	Status       uint8   `json:"status"       gorm:"column:status"`        // 0待执行 1执行中 2成功 3失败 4已过期
	Retry        uint8   `json:"retry"        gorm:"column:retry"`         // 已尝试次数（含首次），领取时 +1
	Reason       *string `json:"reason"       gorm:"column:reason"`        // 最后一次失败原因；成功时 NULL
	ExpiredAt    int64   `json:"expiredAt"    gorm:"column:expired_at"`    // 产出物过期时间（Unix 秒）；0 = 未成功
	LeasedAt     int64   `json:"leasedAt"     gorm:"column:leased_at"`     // worker 最后一次领取或心跳时间（Unix 秒）；0 = 从未领取
	FailedAt     int64   `json:"failedAt"     gorm:"column:failed_at"`     // 本轮退避的计时起点（最后一次失败时间，Unix 秒）；0 = 本轮未失败过
	BaseModel
}
```

**`LeasedAt` / `FailedAt` 是计时列，不是审计列**（§7.1 的两类时间）：它们参与谓词比较，必须由代码显式写，**不能**交给 GORM 自动填；反过来 `updated_at` 是纯审计，不许被业务逻辑读来做判断。四个时间列的职责划分见 §7.1。

### 3.4 类型分层（DB / Go / proto）

三层的选型依据不同，**不要求逐字一致**：

| 层 | 依据 | 类型 |
|---|---|---|
| DB | 容量——不设上限、永不迁移 | `BIGINT UNSIGNED` |
| Go entity / types | 与 DB 对齐 | `int64` / `uint64` |
| proto | **前端能不能解析** | 除 `size` 外一律 `uint32` |

proto 侧的规则来自 **proto3 的 JSON 映射**：gRPC 线上 `int64` 与 `uint64` 都是 varint、无差别；差别只在 JSON——`int32` / `uint32` / `sint32` / `fixed32` 渲染为 **number**，`int64` / `uint64` / `sint64` / `fixed64` / `sfixed64` 渲染为 **string**。这是规范行为，protojson 没有"64 位输出数字"的开关。

**边界转换：按"上界是否已知"分流**：

1. DB ↔ Go：无转换。
2. Go → proto `uint32`：
   - **上界已知、且已写成文档事实**（时间戳、ids、`total`、`chunkCount` 等）→ 允许直接 `uint32(x)`，但该转换点**必须登记**（10-接口契约「已登记的时间戳转换点」）；
   - **上界未知或无上界** → **不得** `uint32(x)`。要么把 proto 改成 `string`（`size` 就是这么处理的），要么在转换处显式校验并报错。
3. `uint64` 字节 ↔ proto `string`：`strconv.FormatUint` / `ParseUint`，解析失败即报错。

### 3.5 单位与字符集口径

**单位**（列名一律不带单位后缀）：

| 项 | 单位 |
|---|---|
| 人工录入配置（`default_max_size` / `max_size`） | **MB** |
| 时间（`temp_url_ttl` / `export_ttl` / 各时间戳） | **秒** |
| 程序写入度量（`object.size` / `upload.total_size` / `export_task.size`） | **字节** |
| API 的 `size` / `chunkSize` | **字节**，与 `object.size` 同单位、无换算 |

规则：**人工录入的配置用 MB / 秒**（让人填 `10485760` 只会填错数量级），**程序写入的度量用字节**（唯一无歧义单位）。

**字符集**：

| 列 | 字符集 | 理由 |
|---|---|---|
| `md5` / `ext` / `upload_id` | `ascii_bin` | 值域已知为 ASCII；`_bin` 保证大小写敏感（用 `_ci` 会让 `jpg`/`JPG` 判成同一个值） |
| `store_keyword` / `app` / `path` / `name` | `utf8mb4_bin` | 含中文或需与 manager 侧 `app.keyword` 逐字对齐 |
| 表级 | `utf8mb4_unicode_ci` | 5.7 可用的、语义最接近 `utf8mb4_0900_ai_ci` 的排序规则 |

**唯一性不依赖表级排序规则**——所有唯一键都显式声明了列级 `_bin`，换表级排序规则不影响任何唯一性判定。

## 4. infra 各组件

### 4.1 `infra/store` registry —— 进程内全量 registry

持有 `map[string]Client`（key = `keyword`），启动时一次性加载，**含 `status=0` 的停用行**。接口与四条实现约定见 02-store。

### 4.2 `infra/dbs/cache.go` —— Redis 读写、延迟双删、重建锁

`app_config` 的读路径要 `temp_url_ttl`，而这张表运行时可改、又必须跨实例失效 ⇒ 必须有共享载体。缓存组件承担三件事：

1. **Redis 读写原语**：`GET` / `SET`（带 TTL）与删除（删除原语叫 **`ClearCache`**，**不叫 `Invalidate`**——那个词在 `.claude/rules/infra-layer.md` 里同时指"软删除（设 `valid_to`）"和"删缓存"，一词两义，见 03-app_config §6.2）。
2. **写路径的延迟双删**：写行之后 `删 key → 延迟 500ms → 再删一次`。**只删、不回填**。本服务**唯一的写触发点是 `app_config.Update`**——该表不提供 `Delete`（03-app_config §1），所以"删除路径也要记得失效"这条义务**不存在**（没有入口的操作不会被误做）。
3. **读路径的重建锁**：`SET lock:{key} <token> NX PX 3000`，抢到者查库回填，放锁用 Lua 比对 token。**只拉、不删**。

**第二次删必须用 `ctx.Clone()` 起 goroutine**（`.claude/rules/main-and-config.md`：`Clone()` 用于脱离请求超时）。否则请求一返回 goroutine 就被取消，第二次删永远不执行，**且没有任何现象**——表现为"配置偶尔不生效"：

```go
// 第二次删：脱离请求上下文，否则随请求 cancel 一起死
go func(ctx core.Context) {
	time.Sleep(cacheDoubleDeleteDelay) // 500ms，代码常量，不做成配置项
	// 删的是本组件自己的 key，不经 repository —— 缓存删除不外露到领域层（见 03-app_config §6.2）
	if err := cache.ClearCache(ctx, appConfigKey(app)); err != nil {
		ctx.Logger().Warnw("msg", "second cache delete error", "key", app, "err", err.Error())
	}
}(ctx.Clone())
```

`500ms` 是**代码常量**、不做成配置项（理由见 11-配置）。缓存键命名、TTL、负缓存、锁的四条实现约定与一致性口径见 03-app_config §2-§3。

**这一层的两个动作在语义上是对称的**：写路径只删、读路径只拉。任何"写完顺手刷一下"的写法都会给缓存引入一个**没有对应失效动作**的值来源，属于本设计明确禁止的形态（见 03-app_config §6.1）。

### 4.3 `infra/store` Client 接口

`Client` 接口定义在 `repository/store.go`、由 `infra/store` 实现，暴露 `Put` / `Get` / `Head` / `Delete` / `NewMultipart` / `ResumeMultipart` / `ListParts` / `Complete` / `Abort` / **`PresignPart`** / `GenTemporaryURL`。详见 02-store。

> `PresignPart`（**上传字节直传厂商**的落地手段，2026-10-13 定，含 `chunkCount=1` 单片）：输入 `uploadId` + `partNumber`，输出厂商的 `UploadPart` 预签名地址。它与 `GenTemporaryURL`（**读侧**签名）是一对，但**语义不同**——前者授的是"往桶里写一片"的能力，后者授的是"从桶里读一份"的能力，**TTL 与配置项也分开**（`upload.partUrlTtl` vs `app_config.temp_url_ttl`）。理由与调用方见 `06-upload.md` §5/§6.2。

> **时间从哪来不是本节的内容**：本设计**不封装 `now()`**、也不把时钟做成一个"组件"——时间由**调用方以参数注入**（见 §7.1）。

## 5. 唯一构造入口

对象键的构造与解析**只能有一个入口**。两处各自拼一次，理解不一致就拼出错误的键，而这类错误在 URL 层面表现为 404，排查时看不出根因。

```go
// pkg/objectkey —— 全项目唯一允许拼对象键的地方，配单测锁死
// ObjectName 由 (md5, ext) 构造对象名；ext 为空时不拼点
func ObjectName(md5, ext string) string
// ExportObjectName 由 md5 构造导出产物名：export/{md5}.zip
func ExportObjectName(md5 string) string
// ParseObjectName 解析对象名；只允许用 filepath.Ext，禁止按段数切分
func ParseObjectName(name string) (md5, ext string, err error)
```

**解析失败必须拒绝，不得回落到默认桶**：host 不在 store map、path 去掉单个后缀段之后不是 32 位小写 hex，两种情况都直接 404。这与"`provider` 不在白名单就启动报错"是同一立场——回落会把配置错误变成静默读错桶。

**同类"唯一入口"清单**：

| 函数 | 包 | 禁止的替代写法 |
|---|---|---|
| `ObjectName` / `ExportObjectName` / `ParseObjectName` | `pkg/objectkey` | 任何 `fmt.Sprintf("%s/%s.%s", ...)` |
| `CanonicalEndpoint` / `AddressingStyle` | `pkg/provider` | 从 host 字符串反推寻址方式 |
| `Size` / `Count` | `pkg/chunk` | `math.Ceil(float64(...))` |
| `Digest`（分片摘要的摘要） | `pkg/chunk` | 单片与分片各写一份（两条路径必须共用，否则同内容得两个身份）；把公式复制到前端 |
| `EscapeLike` / `PrefixPattern` | `pkg/pattern` | 手写 `path + "/%"` |
| `exportMd5` | `domain/service` | 多个导出入口各自算摘要 |

**格式变更只能改这一个函数，并且必须配套迁移**：对象名与键格式是对外承诺——完整 URL 会写进第三方页面和接入方的库，所以 `md5` 段的位置、大小写规则、**后缀取首写者且永不变更**这三点与 `store.keyword` 不可修改同级。变更路径只有"新建 store + 批量拷贝 + CDN 侧 301"。

**`chunkSize` 公式与 `Digest` 一起，构成"对象身份"的完整定义**（2026-10-13 定）：对象键是 `{md5}.{ext}`，而 `md5` = **按 `chunkSize` 切片后逐片摘要再汇总**（06-upload §4.2）。所以**改 `chunkSize` 公式就等于改所有对象的键**，冻结级别与对象名格式同级——这不是"调一个常量"，是换一套命名。客户端**不得**自己实现公式，必须经取片大小接口取值（06-upload §6.1）；服务端的两条路径（统一的 multipart，含 `chunkCount=1` 的单片）也必须**共用 `Digest` 这一个函数**，否则同一份内容会得到两个身份。

## 6. gorm 零值陷阱（必踩清单）

`Updates(struct)` 会忽略零值字段。以下位置**必须显式指定列**：

| 表 | 列 | 为什么是零值但必须写 |
|---|---|---|
| `directory` | `accept` | `''` = 不允许任何类型（用户主动设置的值） |
| `directory` | `max_size` | 值域从 1 起，写 0 应报错而非静默跳过 |
| `file` | `name` / `directory_id` | 改名 / 移动 |
| `export_task` | `status` / `retry` / `reason` / `expired_at` / `leased_at` / `failed_at` | 状态跃迁全部走 CAS；`failed_at = 0`（手动重试复位）与 `expired_at = 0` 都是有语义的零值，**一律用 `Updates(map[string]any)`**（见 §7.2 第 2 条，禁用 `UpdateColumn`） |

`entity` 侧的类型选择也要配合：`reason` 用 `*string`（NULL 有语义 = 成功），`expired_at` 用 `int64`（0 有语义 = 未成功），`upload_id` 用 `*string`（NULL = 秒传/直传）。

## 7. 时间戳与 CAS UPDATE

### 7.1 两类时间列

本设计要求 `created_at` / `updated_at` 由**应用侧**写入（DDL 里不给 `DEFAULT CURRENT_TIMESTAMP`），实际填充者是 GORM。GORM 的行为是（`gorm@v1.31.1/schema/field.go:292-312`、`callbacks/update.go`）：

| 条件 | GORM 行为 |
|---|---|
| 字段名恰为 `CreatedAt` / `UpdatedAt`，且类型是 `Int` / `Uint` 族 | 自动按 **Unix 秒**填充 |
| 走 `Updates(map[string]any)` + `Model(&entity.X{})` | **自动填**（map 分支不受零值跳过影响） |
| 调用 `UpdateColumn` / `UpdateColumns` | **跳过**（`SkipHooks` 生效） |

时间列在本设计里被**刻意分成两类**，不许混用：

| 类别 | 列 | 谁写 | 语义 |
|---|---|---|---|
| **审计时间** | `created_at` / `updated_at` | GORM 自动 | 只回答"这行什么时候被改过"，**任何业务逻辑都不许读它做判断** |
| **计时时间** | `export_task.leased_at` / `export_task.failed_at`、`upload.updated_at` | 代码显式写（`now` 由调用方注入） | 参与谓词比较，是承重字段 |

**三个计时列各自的消费点**（这就是"承重"的含义）：

| 列 | 消费点 | 谓词 |
|---|---|---|
| `export_task.leased_at` | `ReclaimLease` | `leased_at < :now - :lease` |
| `export_task.failed_at` | claim | `failed_at + backoff(retry) <= :now` |
| `upload.updated_at` | upload GC | `updated_at < :now - :sessionTtl` |

**`now` 由调用方注入，不封装**（2026-10-13 定）：涉及时间的仓储方法都把它作为入参（`Claim(ctx, id, now)` / `ReclaimLease(ctx, now, lease)` / `ListExpiredUpload(ctx, before, limit)` …），**`dbs` 实现不自己读时钟**，调用处直接写 `time.Now().Unix()`。统一的是**单位**（Unix **秒**，由 §3.3 的列注释承担）：一处 `Unix()`、一处 `UnixMilli()` 会让谓词静默错位——**表现为退避永不生效或立即生效、没有任何报错**。

**分列的根因**：`updated_at` 一旦同时承担"审计"与"计时"，任何一次无关的 UPDATE 都会静默挪动计时起点——这是**两个不同的量共用一个名字**，属于本设计明令禁止的形态。所以凡是"代码写入一个时间戳、稍后拿它跟 `:now` 比大小"的语义，一律**开专列**；`updated_at` 退回纯审计。

唯一的例外是 `upload.updated_at`：该表的 UPDATE 只有 `TouchUpload` 一条，没有"无关 UPDATE 顶掉计时"的风险，且它是滑动过期的唯一时钟，开专列等于复制一个永远相等的字段。

**两点配套约束**：

1. 时间戳**全部由应用侧写入**（CAS 显式 `SET <计时列> = :now`，不用 DB 的 `NOW()` / `CURRENT_TIMESTAMP`）——否则应用服务器与 DB 服务器之间的时钟偏差会混进这些列，而它们正是被用来做区间比较的。
2. **`gorm.Config.NowFunc` 保持默认**（默认就是 `time.Now`，与调用处写的 `time.Now()` 是同一个函数 ⇒ 审计列与计时列天然同源）。**配自定义函数才会引入第二个时钟**——`NowFunc` 返回 `time.Time`，它取 `.Unix()` 的取整/时区处理与直接调 `time.Now().Unix()` 各自独立。

### 7.2 三条要求

1. `Create` 路径可以依赖 GORM 自动填 `created_at` / `updated_at`（字段名必须保持 `CreatedAt` / `UpdatedAt`）。
2. **CAS UPDATE 必须走 `Updates(map[string]any{...})` 并携带 `Model(&entity.X{})`**，让 GORM 自动填 `updated_at`；**不得用 `UpdateColumn` / `UpdateColumns`**——它们置 `SkipHooks`，会让 `updated_at` 静默不动。同时：
   - map **不得**包含 `updated_at`（否则与自动填冲突，且引入第二个 `now`）；
   - **计时列必须显式写**（`leased_at = :now` / `failed_at = :now` / `failed_at = 0`），它们不是审计列，GORM 不认；
   - 计数器用 `gorm.Expr("retry + 1")` 表达自增，不要先读后写。
3. **承重字段清单**：只有 `export_task.leased_at` / `export_task.failed_at` / `upload.updated_at` 这三个列参与谓词比较（§7.1 表）。改这两张表（`export_task` / `upload`）时**只允许**通过 §8.2 登记的 CAS 语句与 `TouchUpload` 触碰它们，不允许在业务更新里顺手 `Updates` 整行。`updated_at` 不再承重，可自由随行更新。

## 8. 事务与并发约定

### 8.1 事务边界清单

统一用 `ctx.Transaction(func(ctx core.Context) error {...})`，不用原生 `Begin/Commit`；嵌套调用复用外层事务。

| # | 事务 | 内容 | 边界理由 | 详见 |
|---|---|---|---|---|
| T1 | 分片完成 | 确保 `object` 行 + `INSERT file` + `DELETE upload` | file 出生 = 会话死亡，必须原子 | 06-upload |
| T2 | 秒传 | `INSERT file` | 单条写入，无需显式事务（单片现在也走 T1 完成事务） | 05-object、07-file |
| T3 | 导出请求 | `INSERT export_task` + `INSERT export` | `export.app ≡ export_task.app` 靠同事务派生 | 08-导出 |
| T4 | 删目录 | 收集 A + 删 file 子树 + 查 B | **跨事务则一个对象都回收不掉** | 09-回收与后台任务 |
| T5 | 自动建目录 | 逐层 `INSERT IGNORE` + 重查 | 并发靠唯一键，不靠锁 | 04-directory |

**厂商调用一律在事务外**：`PutObject` / `DeleteObject` / `AbortMultipartUpload` 全部放在事务提交之后。T1 的 `CompleteMultipartUpload` 除外——它在厂商侧先完成，DB 事务只是记账。

### 8.2 乐观 CAS 清单（数据面不使用分布式锁）

| 位置 | CAS 条件 | 语义 |
|---|---|---|
| `export_task` claim | `status IN (0,3) AND retry<3 AND failed_at + backoff(retry) <= :now` | 多实例只一个领到 |
| `export_task` 成功 / 失败 | `status=1` | 租约被接管后旧结果不覆盖 |
| `export_task` 手动重试 | `status IN (2,3,4)` | 只允许从终态整轮重来；同时 `retry=0, failed_at=0, expired_at=0`；**过期产物重跑的唯一入口**（自动复活已撤销，08-导出 §5） |
| `export_task` 租约恢复 | `status=1 AND leased_at < :now - :lease` | 心跳停摆的 worker 被接管 |
| `export_task` 产出物清理认领 | `status=2` | 多实例只一个去删桶对象（08-导出 §12） |
| `object` 回收删行 | `id=? AND NOT EXISTS(引用)` | 防删掉刚被引用的行 |
| `directory` 新建 | 唯一键 + `INSERT IGNORE` | 并发隐式建目录 |
| `object` 建行 | `uidx_object_store_md5` 撞键后重查 | 并发同内容上传 |
| `file` 建行 | `uidx_file_upload_id` | 并发重放完成事务 |

上表每一条都是"原子条件更新"，落码时必须满足 §7.2 第 2 条的三条约束（`Updates(map)` + `Model()`、map 不含 `updated_at`、计时列显式写）。

**数据面竞态不使用分布式锁**（2026-10-13 收窄措辞）。乐观 CAS + 唯一索引已覆盖全部竞态点，加锁会引入新的失败模式（锁超时、锁泄漏）。

判据是**"这把锁坏掉时会怎样"**：

| 锁的用途 | 承担 | 坏了会怎样 | 本设计 |
|---|---|---|---|
| **数据面竞态**：谁领任务、谁建行、谁删对象 | **正确性** | 数据错（丢数据 / 重复执行 / 悬空行） | **不用锁**，全部走 CAS |
| **缓存重建**：谁去查库回填（03-app_config §3.2） | **成本** | 每个请求各查一次库，**正确性分毫不差** | 用锁 |
| **导出任务亲和**：哪个实例负责这个导出（08-导出 §7.1） | **成本** | 两个实例各生产一份，同一个键覆盖、字节相同，**正确性分毫不差** | 用锁 |

**全服务共两把分布式锁**（2026-10-13 16:55 定，此前写的是"唯一一把"），都落在"成本"这一档、都不承担正确性。两把的共同点是**失败模式都是"退化为更费的做法"而不是事故**：重建锁退化为直查；亲和锁退化为不检查锁、走全局 claim（= 没有亲和时的行为）。

**这不是"后台任务不做分布式选主"的例外，恰恰是它被取消的证明**：09-回收与后台任务 §6.2 已逐条确认七个后台任务**没有一条需要选主**（各自有自带排他的机制——CAS / 唯一键仲裁 / 谓词幂等 / 任务亲和）。导出 worker 需要的那一点协调由**亲和锁**承担，同样不承担正确性。原先"首版按单实例部署"的规避**已解除**（12-工程与交付 §3.1）。

### 8.3 并发语义总原则

> **宁可留孤儿，不可留悬空行。**

孤儿只是浪费字节、可被离线核对发现；悬空行是文件直接 404，属于"数据看起来坏了"。所有竞态处置都按这条取舍，不追求"零残留"。

## 9. 命名与结构

| 类型 | 规范 | 示例 |
|---|---|---|
| 文件名 | 全小写，下划线分隔 | `app_config.go`、`export_task.go` |
| 包名 | 全小写，无下划线，与目录名一致 | `entity`、`repository`、`dbs` |
| 结构体 / 接口 | 大驼峰，与领域名词对应 | `ExportTask`、`Upload` |
| 方法 | 大驼峰，动词开头 | `PrepareUpload()`、`Claim()` |
| 私有方法 | 小驼峰 | `canonicalEndpoint()`、`escapeLike()` |
| 常量 | 大驼峰或全大写 | `ExportStatusPending`、`maxRetry` |
| 错误函数 | 大驼峰 + `Error` 后缀 | `ParamsError()`、`CreateError()` |
| 错误判断函数 | `Is` 前缀 | `IsParamsError()` |

- **构造函数**：service 用 `NewXxx(...)` 手动注入 repository 接口；infra/dbs 用单例（`sync.Once`）；app 层在 `NewXxx()` 里完成 `service → dbs` 的注入链，并用 `init() + register()` 自注册。
- **注释**：每个公开方法必须有中文注释，以方法名开头；私有方法同样需要注释；entity 字段与配置结构体字段**强制**行尾注释。
- **app 层 handler 三步模式**：① `ctx := core.MustContext(c)`；② `value.Transform(req, &in)` 转换请求，失败返回 `TransformError()`；③ 调 service + 转换响应。
- **对只传 ID 的简单请求可以跳过 Transform**，直接构造 types。

## 10. 错误处理与日志

**错误处理分层**：

| 层 | 做法 |
|---|---|
| infra | 返回原生 error，不做包装 |
| service | 捕获底层 error → `ctx.Logger().Warnw("msg", ..., "err", err.Error())` → 返回 proto 错误函数 |
| app | **直接透传** service 返回的错误，不重新包装 |

禁止：`fmt.Errorf("database query failed: %w", err)` 直接暴露给上层；在 app 层 `errors.New(500, ...)` 重新包装。

**日志键名规范**：`"msg"` 操作描述 / `"err"` 错误信息 / `"key"` 业务键名 / `"id"` 资源 ID。

错误码枚举定义见 10-接口契约。
