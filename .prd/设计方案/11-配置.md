## 1. `business` 段

```yaml
business:
  # ---- 上传与分片 ----
  upload:
    sessionTtl: 24h        # 分片会话过期；GC 按 updated_at 扫
    gcInterval: 5m         # GC 扫描周期
    partUrlTtl: 1h         # 预签名分片 URL 有效期；覆盖"一个批次从下发到传完"，非整份文件
  # ⏸ 以下导出段首版不实现（2026-10-13 定，README §1.1）：配置保留为设计占位，导出功能启动时才读取
  # ---- 导出 ----
  export:
    localDir: static/export   # 设计占位；容量调度与本地清理见 .prd/草案-导出本地目录与容量调度.md（随导出生效）
    lease: 30m                  # 租约时长；单次导出最长耗时的 2~3 倍（P99 基准）
    heartbeat: 10m              # worker 心跳周期（顶 leased_at）；须 < lease，建议 lease/3
    workerCount: 20             # worker 池大小
    retention: 720h             # 请求行保留期（30 天）；须 >= export_ttl 最大值
    cleanupInterval: 5m         # 产出物清理周期（expired_at 到期 → 删桶对象 → status=4）
    leaseReclaimInterval: 1m    # 租约恢复周期（leased_at 超租约 → status=3）
    taskReclaimInterval: 1h     # 任务行回收周期（status IN (2,3,4) 且无 export 引用 → DELETE）
  # ---- 离线对象核对 ----
  objectAudit:
    enable: true
    interval: 24h
    batchSize: 500
  # ---- app_config 缓存 ----
  appConfigCache:
    ttl: 1h                # 兜底 TTL
    negativeTtl: 10s       # 空结果负缓存
```

**`export.lease` 被两处复用**（2026-10-13 16:55 定）：① 导出任务的租约判定（`status=1 AND leased_at < :now - :lease`）；② **导出任务亲和锁的 TTL**（`SET resource:lock:export_task:{id} … NX PX lease`，08-导出 §7.1）。**不新造配置项**——两者要覆盖的窗口本来就是同一个量（"单次导出最长耗时"），拆成两个名字只会多一处要同步的地方。

复用带来一条必须成立的边界：**锁 TTL 必须显著大于"队列等待 + 最大退避"**，否则创建时预定的任务会在排队期间易主（易主不是错误，只是亲和失效）。`lease` 按"单次导出最长耗时的 2~3 倍"取值，余量足够。

**`upload.partUrlTtl` 的语义是"一个批次"，不是"整份文件"**（2026-10-13 定，配合**上传字节直传厂商**）：分片地址是**按批下发**的（`GetUploadPartURLs`，06-upload §6.2，含 `chunkCount=1` 的单片），所以 TTL 只需要覆盖"客户端拿到这一批 → 把这批传完"。取值太短会在传一半时 403（用户可见的失败），太长等于把"拿到 URL 就能写这一片"的窗口放大——**它同时是能力凭证**。按批取的设计正是为了让这个 TTL 能取小。

**它与 `app_config.temp_url_ttl` 是两件事，不要合并**：后者管**读**（临时下载 URL，按 app 配、可被 app 改），前者管**写**（分片上传地址，服务级、不随 app 变）。

配置源：`CONF_HOST` / `CONF_TOKEN` / `APP_NAME` 三个环境变量齐全时走远程配置中心，否则回落 `conf/` 目录下的本地文件。业务配置通过 `ScanWatch("business", ...)` 热更新，全局单例 `conf` 由 `core.Context.Config()` 暴露，**禁止在 service 中直接读配置文件**。

## 2. 三层划分

| 层级 | 例子 | 变更代价 |
|---|---|---|
| **代码常量** | `maxRetry` / `backoff` / `chunkSize` 公式 / `provider` 白名单 / 延迟双删 500ms / 重建锁 TTL 3000ms | 代码发布；改 `chunkSize` 会**打断所有在飞会话**，按代码发布对待 |
| **服务配置**（`business`） | `sessionTtl` / `gcInterval` / `partUrlTtl` / `lease` / `workerCount` / `retention` / 各周期与 TTL | 热更新，重启或下一轮生效 |
| **app 配置**（`app_config` 表） | `default_accept` / `default_max_size` / `temp_url_ttl` / `export_ttl` / `store_keyword` | 运行时可改，走 Redis 延迟双删（03-app_config） |

## 3. 不做成配置项的四样

| 项 | 理由 |
|---|---|
| 延迟双删的 500ms | 它是"读请求从查库到回填的最坏耗时"的工程经验值（500ms–1s），给不出严格上界；配置化会诱导人以为它可精确调优 |
| 重建锁的 TTL 3000ms | 它是"单次查库 + 回填"最坏耗时的宽松上界（实测亚毫秒级）。**它只影响退化成本、不影响正确性**（超时后只是多几次直查），因此没有需要运维调的理由 |
| `chunkSize` 的 5MB 下限 | 由公式与厂商下限推导（全局 5MB，不按厂商分支），另造常量只会多一个要同步的地方 |
| `maxRetry` / `backoff` | 两张两行的表，改动会改变在飞任务的时序 |

## 4. `retention` 为什么是服务配置而不是 app 配置

它是一条**数据保留政策**（"我们留多久历史"），与"这份产物多久后作废"（`export_ttl`，按 app 配）不是同一层级。唯一硬约束：**`retention` 应当 ≥ `export_ttl` 的最大值**，否则会出现"产物还在、请求行已经没了"的空窗（09-回收与后台任务 §6.1）。
