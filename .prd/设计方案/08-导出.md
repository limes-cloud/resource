## 1. 为什么拆成两张表

**产出物**（一份落在桶里的 zip 字节，生命周期 = 生产 → 成功/失败 → 过期删除）与**用户请求**（"某用户要了一份名叫 X 的导出"，生命周期 = 创建 → 一直可查）是两件生命周期完全不同的事。压在一张表里会导致两个后果：

1. **同一份内容被 N 个用户请求 → N 行，每行各带一份 `status`/`size`**，于是"这份产出物成功了没有"有 N 个答案。
2. **引用计数靠按内容摘要 `COUNT(*)`**——产出物的生死由"请求行的条数"隐式决定，这是派生值当真相。

拆完之后"重试"天然落在正确的层级：重试的是**产出物的生产**，与"有几个用户要它"无关。

## 2. 仓储接口

```go
// repository/export.go
type ExportTask interface {
	// GetExportTaskByMd5 去重判定（必须带 app 限定）
	GetExportTaskByMd5(ctx core.Context, app, md5 string) (*entity.ExportTask, error)
	// ListExportTaskByIDs 主键批量（列表页第二条 SQL）
	ListExportTaskByIDs(ctx core.Context, ids []uint64) ([]*entity.ExportTask, error)
	// CreateExportTask 建任务；撞 uidx_export_task_app_md5 时重查复用赢家
	CreateExportTask(ctx core.Context, ent *entity.ExportTask) (uint64, error)
	// ListClaimable 轮询候选（status=0，或 status=3 且退避到期）
	ListClaimable(ctx core.Context, now int64, limit int) ([]uint64, error)
	// Claim 原子领取：CAS + retry+1 + leased_at=now，RowsAffected==1 才算领到
	Claim(ctx core.Context, id uint64, now int64) (bool, error)
	// MarkSuccess 成功：CAS status=1，写 size / expired_at（updated_at 由 GORM 自动维护）
	MarkSuccess(ctx core.Context, id uint64, size uint64, expiredAt int64) (bool, error)
	// MarkFailed 失败：CAS status=1，写 reason / failed_at=now（退避起点）
	MarkFailed(ctx core.Context, id uint64, reason string, now int64) (bool, error)
	// ManualRetry 手动重试：CAS status IN (2,3,4)，复位 retry / failed_at / expired_at
	ManualRetry(ctx core.Context, id uint64) (bool, error)
	// ReclaimLease 崩溃恢复：status=1 且 leased_at 超租约
	ReclaimLease(ctx core.Context, now, lease int64) (int64, error)
	// ScanExpired 过期产出物扫描（status=2 AND expired_at<=now）
	ScanExpired(ctx core.Context, now int64, limit int) ([]*entity.ExportTask, error)
	// MarkExpired 删桶对象后标记 status=4
	MarkExpired(ctx core.Context, id uint64) error
	// ScanReclaimable 任务行回收：status IN (2,3,4) 且无 export 引用
	ScanReclaimable(ctx core.Context, limit int) ([]*entity.ExportTask, error)
	// DeleteExportTask 删任务行
	DeleteExportTask(ctx core.Context, id uint64) error
}

type Export interface {
	// ListExport 请求行分页（走 idx_export_app_user）
	ListExport(ctx core.Context, app string, userID uint64, req *types.PageRequest) ([]*entity.Export, uint32, error)
	// CreateExport 建请求行
	CreateExport(ctx core.Context, ent *entity.Export) (uint64, error)
	// ExistsByTaskID 回收反查：SELECT 1 FROM export WHERE task_id=? LIMIT 1
	ExistsByTaskID(ctx core.Context, taskID uint64) (bool, error)
	// DeleteExpired 请求行过期清理（created_at < now - retention）
	DeleteExpired(ctx core.Context, before int64, limit int) (int64, error)
}
```

**关于 `now` 参数**：只出现在“**需要把 `now` 写进计时列或参与谓词比较**”的方法上。`updated_at` 已交 GORM 自动维护，因此 `MarkSuccess` / `ManualRetry` / `MarkExpired` 都不再接收 `now`——多传一个 `now` 只会让调用方以为它在写某个时间列，实际被忽略，属于“参数在撒谎”。`MarkSuccess` 的 `expiredAt` 由调用方按 `time.Now().Unix() + export_ttl` 算好传入。

## 3. 产出物身份 = `(app, md5)`，跨 app 不共享

`md5` 是**产出规格**的摘要，不是 zip 字节的摘要——请求到达时 zip 还不存在，而**去重必须在那一刻完成**，所以只能对"产出规格"取摘要；规格确定 ⇒ 产出物确定，因此它仍是产出物的内容身份。反面做法（拿产出后的 zip 字节算 md5 当身份）不可行：zip 内含文件时间戳，同一规格两次生产的字节可以不同，身份会漂。

### 3.1 摘要口径

```
md5 = MD5( canonical( headers, rows, files(value+rename), keys ) )
```

- **纳入**：`headers`、`rows`、`files`（含 `rename`）、`keys`——凡是会改变 zip 内容的。
- **排除**：`name`（展示名）、`user_id`、请求时间——凡是**不改变 zip 内容**的。
- **要求 canonical 序列化**：键序、浮点/空值表示必须稳定。Go 的 `json.Marshal` 对 struct 是稳定的、对 `map` 不是——必须用 struct 或显式排序。

**`name` 不进 `md5`、不进 zip**，它只在**下载时**作为 `Content-Disposition` 的文件名应用。xlsx 在 zip 内的固定名用中性名（如 `data.xlsx`）。这样"同内容不同名"才能真正共享产出物——这正是导出作为重任务最该省的那部分算力。

## 4. 产出物对象键与落桶

**对象键**：`export/{md5}.zip`，一层平铺。

**`export/` 前缀是刻意的**：本项目的"不带前缀"规则针对的是 **store 段**和**日期/哈希分层**，理由是"键必须能由列推导"。`export/` 是**功能命名空间**，仍是 `(md5)` 的纯函数，不违反该规则。它解决一个真实冲突：若导出产物与用户上传共用同一个桶（`export_store_keyword` 为 NULL 时就是），键空间会重叠——用户上传一份同名 zip 就可能与导出产物撞同一个 key，删任一边会删掉对方。

**`store_keyword` 在创建任务时写死**：由 `app_config.export_store_keyword`（NULL 时回落 `store_keyword`）解析后写入。此后 app_config 改配置**不影响历史产出物**——与 `object.store_keyword` 同一条立场（"现在写去哪" vs "当时写去了哪"）。

**导出产物不进 `object` 表**：`object` 的不变式是"**回收只看 `file` 引用**"。导出产物是 **TTL 驱动**、不是引用驱动，塞进 `object` 就要给回收侧加第二个引用来源，破坏那条不变式；而共享性已由 `(app, md5)` 在任务层解决，`object` 的按内容去重在这里没有增量收益。

## 5. 写路径

```go
md5 := exportMd5(spec)   // 口径见 §3.1
task, err := repo.GetExportTaskByMd5(ctx, app, md5)
switch {
case notFound:
	// INSERT export_task(status=0, retry=0, store_keyword 从 app_config 解析) + INSERT export
	// 撞 uidx_export_task_app_md5 则重查复用赢家
	// 紧接着抢亲和锁：SET resource:lock:export_task:{id} <me> NX PX lease（§7.1）
	//   此刻无竞争者 ⇒ 必然成功；失败（Redis 抖动）不拒绝请求，退化为不预定
case task.Status == 2 && task.ExpiredAt > now:
	// 秒传，零算力：只 INSERT export
case task.Status == 2 && task.ExpiredAt <= now, task.Status == 4:
	// 已过期（2026-10-13 定：自动复活撤销）：只 INSERT export，不改任务行状态
	// —— 判据是行的 expired_at，不是桶里文件是否还在（清理线扫没扫到、删没删成功都是过程）
	// 重跑只能走用户手动重试（§8，CAS IN (2,3,4)）；清理线随后 2→4 删桶对象
case task.Status == 0 || task.Status == 1:
	// 排队 / 生产中，INSERT export 返回（前端轮询）
case task.Status == 3 && task.Retry < maxRetry:
	// 重试中，INSERT export 返回
	// 可选（默认不做）：把 failed_at 提前到 :now - backoff(retry) 让退避立即到期 —— 见 §8 注
case task.Status == 3 && task.Retry >= maxRetry:
	// 终态失败，INSERT export 返回；前端提供"重试"按钮
}
```

**`store_keyword` 解析必须校验 `app_config` 存在**——缺行即报"应用未配置"，不回落到服务级默认。

**过期产物不自动复活（2026-10-13 定，替代原"复活"设计）**：请求路径对 `expired_at <= now`（含 `status=4`）的任务**只读不写**——只 `INSERT export` 返回，前端展示"已过期"并提供重试按钮（走 §8 的手动重试）。三条理由：

1. **消除争抢**：清理线的谓词是 `status=2 AND expired_at<=now`（**写**行），原复活分支的谓词与它逐字相同（也**写**行）⇒ 两个写路径相争；改为只读后，写侧谓词天然不相交——清理线独占过期行的写，请求路径只插请求行——**冲突结构性消失**，不再需要把复活 CAS 放宽成 `AND status IN (2,4)` 那类补丁。
2. **原复活窗口本身没有价值**：清理线 5 分钟一轮，原复活只在"已过期但还没扫到"的几分钟内有效；之后任务行以 `status=4` 长眠（等请求行散尽，最长 `retention` 30 天），这段时间里自动复活对同规格请求 100% 失效。为几分钟的窗口背一个与后台线相争的写路径，不划算。
3. **"文件还在"不是事实判据**：桶里是否还有字节，取决于清理线扫没扫到、`DeleteObject` 成没成功——都是过程状态；行的 `expired_at` 才是"这份产物作废了没有"的唯一事实（与读路径"以 `object` 行为准、不以 `app_config` 为准"是同一条立场）。

**显式接受的代价**：用户再次请求同一份导出时不再"无感重跑"，需多点一次重试。按 `export_ttl` 默认 7 天，这是低频的显式行为，不是默认路径。

**手动重试因此成为重跑的唯一入口**：它本来就是"从终态整轮重来"（§8），`expired_at=0` 随 `retry=0` / `failed_at=0` 一起复位——原复活 SQL 与它只差一个 `expired_at`，撤销复活后两条路合并为一条，`status=0 ⇒ failed_at=0` 不变量的维护者也从"手动重试 + 复活"收敛为**手动重试一个**（SQL 设计 §7.1）。

**事务 T3**：`INSERT export_task` + `INSERT export` 同事务，`export.app ≡ export_task.app` 靠同事务派生。

## 6. 状态机

```
        创建                领取(claim)              生产成功
  (0) 待执行 ─────────────► (1) 执行中 ─────────────► (2) 成功 ──[过期]──► (4) 已过期
        ▲                       │
        │ 退避到期(failed_at    │ 生产失败
        │  + backoff(retry))    ▼
        └─────────────────── (3) 失败 ──[retry>=maxRetry]──► 终态(仍为 3，不再被领取)
                                │                                 └─ 由 09-回收与后台任务 回收
     手动重试(复位 retry=0,     ─────┘   CAS: WHERE id=? AND status IN (2,3,4)
              failed_at=0, expired_at=0)
```

**终态 = {2 成功, 3 失败(重试耗尽), 4 已过期}**，手动重试只从这三个状态出发；`0` / `1` 不接受手动重试。

**计时列与状态的不变式**：

| 状态 | `leased_at` | `failed_at` | 说明 |
|---|---|---|---|
| `0` 待执行 | 0 | **0** | 新建与手动重试复位后的形态。`failed_at=0` 让它在 `ORDER BY failed_at ASC` 里落在队首（不是"让退避立即到期"——`status=0` 本来就是独立的 OR 分支，无条件可领） |
| `1` 执行中 | > 0（心跳持续顶） | 保留上一轮值 | 领取只写 `leased_at`，不清 `failed_at`；旧值不参与任何 `status=1` 的谓词 |
| `3` 失败 | 保留 | **> 0**（本轮失败时刻） | 退避从这一刻起算；两条写入路径（`MarkFailed` / `ReclaimLease`）都写 `:now` |
| `2` / `4` | 保留 | 保留 | 不参与计时 |

**两个"不可能状态"，可直接当告警条件**：`status=0 AND failed_at > 0`（队列里的行不该有退避起点）、`status=3 AND failed_at = 0`（失败的行必须有退避起点）。它们不可能出现，是因为 `status` 与 `failed_at` 只在 §7 / §8 那几条 CAS 语句里成对写入。**任何一处漏写都会在这里暴露**，而不是变成一个安静的调度错位。

**常量（写在代码里）**：

```go
const maxRetry = 3                                                     // 最多尝试 3 次（含首次）
var backoff = [3]time.Duration{0, 30 * time.Second, 120 * time.Second} // 索引 = retry
```

`retry` 上限 3 时退避表只有两个非零值，所以它不是"参数"，是一张两行的表——这正是把它写进代码而不是做成配置的依据。

## 7. 领取（claim）—— 乐观 UPDATE + 任务亲和

```sql
-- 轮询候选
SELECT id FROM export_task
 WHERE ( status = 0
         OR ( status = 3 AND retry < 3
              AND failed_at + CASE retry WHEN 1 THEN 30 WHEN 2 THEN 120 ELSE 0 END <= :now ) )
 ORDER BY failed_at ASC, id ASC
 LIMIT :n;

-- 领取（原子）
UPDATE export_task
   SET status = 1, retry = retry + 1, leased_at = :now
 WHERE id = :id AND status IN (0,3) AND retry < 3
   AND ( status = 0
         OR failed_at + CASE retry WHEN 1 THEN 30 WHEN 2 THEN 120 ELSE 0 END <= :now );
```

`RowsAffected == 1` 才算领到。多实例并发时只有一个能改到。

**`ORDER BY failed_at ASC, id ASC` 里 `failed_at` 恰好就是"排队起始时刻"**：`status=0` 的行 `failed_at=0`（不变式），自然排在最前；`status=3` 的行按失败时刻排序，越早失败越早被重试。所以不需要给 `status=0` 补一个假的偏移量，也不需要按 `status` 再分一档排序。**`id ASC` 是必要的次级键**——同一批同时失败的行 `failed_at` 完全相同，没有次级键时分页/排序不稳定。

**`retry` 是"已尝试次数（含首次）"，每次领取 +1**（不是每次失败 +1——崩溃在途的尝试也必须计数，否则一份必然失败的任务会无限重跑）。因此 `retry < 3` 的语义是"总共最多执行 3 次"，不是"首次之外再重试 3 次"。

**领取不清 `failed_at`**：`status=3 → 1` 时保留上一轮失败时刻。这样若本次又失败，`MarkFailed` 覆盖它；若本次崩溃被租约恢复，`ReclaimLease` 覆盖它。两条路径都会重写，保留旧值不会泄漏到任何谓词里。

**为什么不存 `next_retry_at`**：三条理由，前两条在本设计改专列后依然成立——

1. **它是"策略"而不是"事实"**。`failed_at` 记录的是**已经发生的事**（这一轮在何时失败），`next_retry_at` 记录的是**代码里的 `backoff` 表算出来的结论**。把策略结论落库，等于把 `backoff` 表冻进数据：哪天把 `[0, 30s, 120s]` 调成 `[0, 60s, 300s]`，历史行里存着的旧结论立刻全部作废，得做一次回填迁移。代码常量改了就该全局立即生效，不该有历史包袱。
2. **它是可推导的**（`next_retry_at ≡ failed_at + backoff(retry)`），且推导只用到两个同表的列，零额外 IO。
3. 存它意味着**每一个写 `failed_at` 的地方都必须同步写 `next_retry_at`**（失败、租约恢复、手动重试复位、以及未来任何新增的复位点），这是一个人为制造的不变式，漏一处就是静默的调度错误。

**代价明确接受**：退避谓词 `failed_at + backoff(retry) <= :now` 是非 sargable 的，不能在索引上做 range。但候选集 `status IN (0,3)` 在健康系统里天然很小（任务被 worker 快速领走），索引 `idx_export_task_claim(status, failed_at)` 先把它缩到这一小撮，残差过滤在内存里做。**索引第二列选 `failed_at` 而不是 `id`**：`failed_at` 既是排序键又是过滤键的输入，让索引能同时服务 `ORDER BY` 的定位；`status=0` 的行 `failed_at=0` 全部聚在索引最左侧，正好也是 `ORDER BY` 想要的顺序。

### 7.1 任务亲和：创建时拿锁，谁拿谁负责到底（2026-10-13 16:55 定）

**多实例部署下，一个导出任务由"创建它的那台机器"负责全程**（含后续重试）。理由是导出**涉及本地处理**（`static/export` 那份中间产物）——让同一份产物只落在一台机器上，省掉"多台机器各生产一遍"的算力与磁盘。

**载体是一把 Redis 锁**：`resource:lock:export_task:{id}`，value = 实例标识，**TTL = `export.lease`**。**复用租约时长、不新造配置项**——它要覆盖的窗口与"单次导出最长耗时"本来就是同一个量（11-配置 §1）。

三个触点：

| 时机 | 动作 | 说明 |
|---|---|---|
| **创建**（§5 的 `notFound` 分支） | `SET key <me> NX PX lease` | 此刻**没有竞争者** ⇒ 必然成功 ⇒ 任务被"预定"给接收请求的这台机器 |
| **claim 前**（下面那条 CAS 之前） | 先 `SET key <me> NX PX lease`；失败则 `GET key` 比对 | 是自己 ⇒ 续期后继续 claim；是别人 ⇒ **跳过该候选**，看下一个 |
| **生产中**（`status=1` 心跳） | 与顶 `leased_at` **同一个动作**里续 TTL | 保证在跑的任务锁不丢 |

**移交不需要任何新机制**：owner 实例挂掉 ⇒ 心跳停 ⇒ 锁 TTL 到期 ⇒ 锁消失 ⇒ 任何实例的下一次轮询都能抢到并接管。**不需要"在线实例表"，也不需要额外的移交任务**——Redis 的 TTL 免费给出这个语义。

**不给 `export_task` 加 `owner` 列**：所有权是**易失**的（有 TTL、会自然过期）。落库就得有人清它，而"谁清"正是需要"在线实例表"才能回答的问题——那是一个只为这一件事存在的新组件。TTL 到期即释放，是更省的正确形态。

**失败模式是"退化为旧行为"，不是"拒绝服务"**（与 `app_config` 重建锁同一条原则）：

- 创建时拿锁失败（Redis 抖动）⇒ **不拒绝请求**，只是不预定，锁留给第一个 claim 的机器；
- worker 抢不到锁 ⇒ 跳过该候选、继续看下一个；
- **Redis 整体不可用** ⇒ **退化为不检查锁、走全局 claim**（= 没有亲和时的行为）。

**为什么可以这样退化**：这把锁**不承担正确性**——即使两个实例同时跑到，`MarkSuccess` 的 `WHERE status=1` CAS 只有一个能成功，物理产出物又是同一个键 `export/{md5}.zip`（覆盖、字节相同、无害）。锁的作用只是**省算力与省本地磁盘**。⇒ 属于"成本"类锁，与重建锁同类（01-基础设施 §8.2）。

**显式接受的代价**：亲和意味着"创建它的机器优先处理它"，全局 FIFO 退化为**近似 FIFO**——被锁跳过的候选会让位给后面的候选。积压时同一台机器上的任务仍按 `failed_at` 序处理。

**前提（部署形态）**：本设计假定**每个实例同时承载 API 与 worker**。若 API 与 worker 分离部署，"接收请求的机器"没有 worker 去消费，锁会空占 `lease` 后自然过期 ⇒ **亲和不生效、退化为旧行为**——不是错误，只是没生效（12-工程与交付 §3.1）。

**一条边界**：锁 TTL（`lease`，默认 30m）必须**显著大于"队列等待 + 最大退避"**，否则创建时预定的任务在排队期间就易主。`lease` 本来就是按"单次导出最长耗时的 2~3 倍"取的，余量足够；积压超过 `lease` 时亲和失效，但任务仍会被别的实例正常领走。

## 8. 成功 / 失败 / 崩溃恢复 / 手动重试

**成功**：

```sql
UPDATE export_task
   SET status = 2, size = :size, expired_at = :now + :export_ttl,
       reason = NULL
 WHERE id = :id AND status = 1;
```

`export_ttl` 取自该 app 的 `app_config.export_ttl`。`status = 1` 作为 CAS 条件：若租约已过期被别的 worker 接管，这次 UPDATE 不生效，**不会用旧结果覆盖新状态**。`updated_at` 不再显式写——它是审计列，交给 GORM。

**失败**：

```sql
UPDATE export_task
   SET status = 3, reason = :err, failed_at = :now
 WHERE id = :id AND status = 1;
```

**`failed_at = :now` 就是退避的起点**，退避值本身不写库——它是 `failed_at` 与 `retry` 的函数（`failed_at + backoff(retry)`），读的时候现算。`retry >= maxRetry` 时**不需要任何终态标记**：领取查询的 `retry < 3` 条件自然让它再也取不到。这就是**终态失败**：不自动复活、不会自动重跑，同规格的新请求只会拿到"失败"，只有手动重试能救。

**崩溃恢复（租约）**：

```sql
UPDATE export_task
   SET status = 3, reason = 'worker lease expired', failed_at = :now
 WHERE status = 1 AND leased_at < :now - :lease;
```

- **执行中的 worker 必须周期性顶 `leased_at`**（心跳），`lease` 取"单次导出最长耗时的 2~3 倍"。否则一份大导出会在传输途中被误判成僵死。
- **租约单独用 `leased_at`，不复用 `updated_at`**。原因：`updated_at` 会被**任何**一次对该行的 UPDATE 顶掉——审计补写、运维改字段、未来新增的任何一条 UPDATE 都会刷新它，于是"worker 还活着吗"这个判断会被无关操作污染成"看起来一直活着"，僵死任务永远不被回收。`leased_at` 只有心跳和领取会写，是**单一职责**的，这个语义必须由列结构保证而不是靠纪律。
- 回收时写 `failed_at = :now` 而不是保留旧值：租约超时是一种**失败**，退避必须从此刻重新起算，否则一个反复僵死的任务会以旧时间戳立即被再领走，形成热循环。
- 租约超时后原 worker 可能还活着并最终写成功。此时它的 `WHERE status=1` CAS 会失败——**幂等由 CAS 保证，不靠互斥**。而物理产出物键是 `export/{md5}.zip`，重复生产是**覆盖同一份字节**，无害。

**手动重试**：

```sql
UPDATE export_task
   SET status = 0, retry = 0, reason = NULL, failed_at = 0, expired_at = 0
 WHERE id = :id AND status IN (2, 3, 4);
```

**`expired_at = 0` 与 `retry = 0` / `failed_at = 0` 必须同写**（2026-10-13 补）：`expired_at` 的语义是"0 = 未成功、还没有产物"（§1 字段说明）。从 `status=2/4` 手动重试的行带着一个过去的 `expired_at` 回到队列，在 worker 重新生产成功前会一直显示"已过期"——把一列**过程残留**暴露给读路径。复位为 0 后，"排队中 = 无产物"在行上自明，与新建任务的形态一致。

**`status IN (2,3,4)` 这个 CAS 条件不能省**：只允许从**终态**重试。少了它，一次点击就会把正在跑的 `status=1` 打回待执行——worker 随后的 `WHERE status=1` 成功 CAS 失败、结果被丢弃，而任务被重跑一遍，等于白烧一份算力还多产出一份字节。`RowsAffected = 0` 时返回"当前状态不可重试"，前端据此禁用按钮。**它同时是过期产物重跑的唯一入口**（自动复活已撤销，§5）：`status=4` 的行由此回到 `status=0`，worker 重新生产、写回同一个键 `export/{md5}.zip`。

**`failed_at = 0` 与 `retry = 0` 必须同写**，两条真实理由：

1. **不变式 + 排序正确性**。本册定义的不变式是 `status=0 ⇒ failed_at=0`，而候选查询的 `ORDER BY failed_at ASC` 依赖它——`status=0` 的行全部 `failed_at=0`，自然聚在队首。若手动重试不复位，一条"刚被人工唤醒"的任务会带着两小时前的旧时间戳排在队中段，**排队位置与它的语义完全脱节**；复位后它回到队首，符合"人点了重试就该尽快跑"的直觉。
2. **让异常态可 grep**。`status=0 ∧ retry=0 ∧ failed_at=0` 三者同现才说明这是一条干净的任务。反过来，`status=0 AND failed_at > 0` 是一个**不可能状态**，运维可以直接拿它当告警条件扫异常行。允许它存在，就等于放弃了这个信号。

> 注意一个容易搞反的点：**不复位 `failed_at` 并不会"绕过退避"**。候选查询里 `status = 0` 是一个独立的 OR 分支，`status=0` 的行**本来就无条件立即被领走**，`failed_at` 取什么值都不参与判断。所以"退避被绕过"不是这里的理由——真正的理由是排序与可观测性。

**`leased_at` 不在这里复位**：它是"最后一次领取"的痕迹，留着它能让运维看出"这条任务被人工唤醒前是什么时候跑的"。它不参与任何针对 `status=0` 行的谓词。

`status=0` 的行也**不**接受手动重试：按不变式它已经是 `retry=0 ∧ failed_at=0`，重置是个纯 no-op（只多顶一次 `updated_at`）；语义上"已在队列里的任务"也没有"重试"可言。

**可选：让已失败任务插队（默认不做）**。若希望"同规格的新请求把已失败的任务提到队首"，**不能**把 `failed_at` 写成 `0`——那会违反 `status=3 ⇒ failed_at>0`（失败的行必须有退避起点），同样污染 §6 的告警哨兵。正确写法是让它"假装已经等够了"：

```sql
UPDATE export_task
   SET failed_at = :now - CASE retry WHEN 1 THEN 30 WHEN 2 THEN 120 ELSE 0 END
 WHERE id = :id AND status = 3 AND retry < 3;
```

此时 `failed_at + backoff(retry) = :now`，谓词立即成立，而 `failed_at` 仍是正数。**代价**：这是请求路径上的一个副作用写（多一条 CAS UPDATE、多一处并发失败要处理），而收益只是排序提前。**默认不做**——把"插队"留给显式的手动重试更干净。

**实现注记（五条 CAS UPDATE 通用）**：

1. 一律用 `Updates(map[string]any{...})` 且必须携带 `Model(&entity.ExportTask{})`（GORM 靠它拿到 schema 才能自动填 `updated_at`；不带 `Model` 的 map 更新会因 `stmt.Schema == nil` 而**静默跳过**时间戳填充）。
2. **不得用 `UpdateColumn` / `UpdateColumns`**——它们置 `Statement.SkipHooks = true`，自动时间戳回调被跳过。
3. map **不得包含 `updated_at`**；计时列（`leased_at` / `failed_at`）必须显式写，GORM 不认它们。
4. `retry` 用 `gorm.Expr("retry + 1")` 表达自增，不要先读后写。
5. 所有 `:now` 都是**调用方传入的 `int64`**（`time.Now().Unix()`，单位必须是**秒**；01-基础设施 §7.1）——`dbs` 实现不自己读时钟，也不封装 `now()`。

## 9. 为什么不做"按 md5 找回会话"式的重试

导出是**无状态纯函数**（输入 = 规格，输出 = zip），没有厂商侧会话、没有部分进度可续。所以重试 = **整份重跑**。这也意味着**重试成本高**，所以 `maxRetry` 只给 3，且**去重命中要尽可能前置**（§3.1 的摘要口径是提高命中率的关键）。

## 10. 列表读——固定两条 SQL

```sql
SELECT ... FROM export WHERE app=? AND user_id=? ORDER BY id DESC LIMIT 20 OFFSET ?;
SELECT id, status, size, expired_at, reason, retry, failed_at FROM export_task WHERE id IN (...);
```

第二条走主键。**不允许退化成每行一次点查**。`retry` / `failed_at` 与其余列同在一行，多选两列不增加任何 IO，但**换来"下次重试时间"可以现算**：由服务端按 `failed_at + backoff(retry)` 算出后返回，不落库——理由同 §7（策略不落库）。不展示该字段时忽略这两列即可，不要为它再拆一条 SQL。

## 11. 下载

URL 由 `store_keyword` + `ExportObjectName(md5)` 拼出。**下载时把请求行的 `name` 作为 `Content-Disposition` 文件名**，不依赖 zip 内部命名。

## 12. 回收

三条独立的导出清理线（产出物过期 → 任务行回收 → 请求行过期）构成闭环，完整说明与后台任务注册在 **09-回收与后台任务**。

**第 1 条（产出物过期）在多实例下必须带 CAS**（2026-10-13 16:55 补）：

```sql
-- 认领"由我负责删这个桶对象"，RowsAffected==1 才去删
UPDATE export_task SET status = 4 WHERE id = ? AND status = 2;
-- 1 → DeleteObject(store_keyword, ExportObjectName(md5))；0 → 跳过，别人在做
```

**为什么不能只靠"`status=4` 防重复删"**：那句话只防**下一轮**。同一轮里两个实例都在 `expired_at<=now` 的那一刻扫到 `status=2`，两边都会去删桶对象。而 `export/{md5}.zip` 是**同规格共用的键**：若期间有新请求把这份产出物重新生产出来（复活 → 重跑 → 写回同一个键），后一个实例的 `DeleteObject` 会删掉**刚生产出来的那份**。CAS 把"谁负责删"收敛成单点——与 §5「离线对象核对」第 2 步的 CAS 是同一个形态。

> **已结（2026-10-13 定，原"复活 vs 清理谓词冲突"）**：冲突的根因是原"请求路径复活"分支与清理线**谓词逐字相同且都写行**（都是 `status=2 AND expired_at<=now`）。自动复活撤销后（§5：过期产物只读返回、重跑走手动重试），写侧谓词不相交——清理线独占过期行的写，请求路径只 `INSERT export`——**冲突结构性消失，不需要 `AND status IN (2,4)` 之类补丁**。
>
> 残留的唯一交叠是**手动重试**（CAS `IN (2,3,4)`）与清理线撞同一行：只有一方 CAS 成功，且若手动重试赢在 `DeleteObject` 之前，清理线的删除会落到新产物上。窗口是毫秒级、由用户显式触发，后果是"该次重跑的产物没了、下次重试再跑一遍"——**显式接受**。同样的窄窗在"两个实例同轮都扫到 `status=2`"时也存在，由 CAS `2→4` 收敛为单点（本节上文）。
