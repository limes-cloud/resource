# 测试规范（本服务专用）

> 适用范围：`server/resource`。本节是**准入规则**，与 `.prd/设计方案/` 的分工是：
> 设计文档说"什么是对的"，本规则说"什么值得写成自动化测试"。

## 1. 一条规则

> **单测只覆盖工具函数；业务逻辑一律通过请求接口验证。**

| 类别 | 是否写单测 | 怎么验证 |
|---|---|---|
| 工具函数 / 纯函数 | ✅ 写 | 直接调用，输入决定输出 |
| 业务逻辑（service 编排、状态机、CAS） | ❌ 不写 | 启动服务后请求接口 |
| 仓储实现（dbs 的 SQL、缓存协议、延迟双删） | ❌ 不写 | 启动服务后请求接口 |
| 请求 DTO（types） | ❌ 不写 | 随接口一起验证 |
| proto 契约（字段类型、JSON 形态） | ❌ 不写 | 启动服务后看真实响应 |

## 2. 「工具函数」的判定标准

三条同时满足才算：

1. **不依赖外部状态**——不碰 DB / Redis / 厂商 API / 网络 / 时钟 / 文件系统；
2. **不依赖业务上下文**——不需要先有 store 行、app_config 行、上传会话这些业务事实；
3. **确定性**——同样的输入永远得到同样的输出，不需要 mock 任何协作者。

按这个标准，本服务的工具函数集中在 `internal/pkg/`（`objectkey` / `chunk` / `pattern` / `provider`），
以及少数同性质的无 I/O 结构（如 `infra/store` 的内存 registry）。

**不得为以下东西写测试**：getter、字符串常量、配置结构体字段、以及"断言一段 SQL 文本长什么样"
——后者一旦重构 SQL 就红，但它证明不了行为对错。

## 3. 为什么不为业务逻辑写单测

- **mock 的收益是负的**。一旦给 repository 造内存假实现，测试维护的是"假实现的行为"，
  假实现与真实 GORM/MySQL 的偏差（零值跳过、`Updates(map)` 的自动时间戳、唯一键错误码、
  事务的"读己之写"）全部测不到，却每次改接口都要同步改假实现。
- **并发与一致性无法单测**。延迟双删的窗口、重建锁的 Lua 比对、完成事务的原子性、
  多实例下的 CAS 仲裁——这些的正确性只能在真实链路上观察。
- **真正的坑在接口上**。字段类型（`size` 是 string 而 `chunkSize` 是 number）、
  错误码、鉴权、分页边界，这些"看起来对"的东西最容易出错，而它们只有打到真实响应才算验证。

## 4. 业务逻辑怎么验：请求接口

启动服务后打真实接口（HTTP 或 gRPC），按功能点逐条核对。可操作的做法：

```bash
# 1. 起依赖（MySQL + Redis）并建表
mysql -uroot resource < deploy/schema.sql

# 2. 启动服务
go run main.go

# 3. 打接口核对行为（示例）
curl -s localhost:7020/<接口路径> | jq
```

每个功能点交付时，在交付说明里列一份**请求级验收清单**（正常路径 + 每个拒绝分支各一条），
逐条核对后再进入下一个功能点。清单要具体到"给什么输入、期望什么响应"。

至少必须覆盖的拒绝分支（这些是静默错误的高发区）：

- `size` 不符 → 拒绝，且 `object` 行不变、桶里零新增
- 摘要核验不符 → 不合并、`Abort`、桶里零残留
- `app_config.status=0` / `store.status=0` → 拒绝新建，存量 URL 仍可读
- `provider` 不在白名单 → 拒绝
- 撞唯一键 → 复用赢家行，而不是报错或覆盖
- `sk` 不出现在任何响应里

## 5. 当前阶段的过渡说明

**S7（接口层）落地之前没有对外接口**，因此 S1–S6 的业务逻辑暂时只能以
`go build` / `go vet` / 代码评审为验证手段。这是阶段性的，不是豁免——
接口一旦补齐，必须回头把上面的验收清单补打一遍，并在每个功能点的交付说明里附上核对结果。
